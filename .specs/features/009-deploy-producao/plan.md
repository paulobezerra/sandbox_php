**User validation to start Code:** Paulo Bezerra validated this Plan by stating “aprovar” on 2026-10-19.

## Delivery strategy

Implement the release and deployment workflow as one integrated task: pull requests run the required checks, a passing merge to `main` creates and deploys an immutable tagged source/build pair, and an operator can select a published tag for redeployment through the same installer. Keep the build on CI, use the existing deployment target and forward-only migration behavior, and keep infrastructure access values in protected settings or host-local configuration. This single-task shape follows the user's explicit direction; it combines workflow, package, installer, and operator documentation changes so the complete workflow can be verified together.

## Tasks

- [x] **T009-01 — Pull request checks, automatic tagged deployment, and manual tag redeployment work as one release workflow.** **Requirements:** S009-01, S009-02, S009-03. **Precondition:** The validated Spec and existing frontend lockfile, test/build commands, release workflow, and shared-hosting installer are available. **Scope:** Complete the GitHub Actions workflow, release payload/package handling, `tools/deploy-shared-hosting.sh`, focused installer/package coverage, and operator documentation needed for all three Spec flows. Run PHP and frontend tests and the production frontend build for pull requests to `main`; on a passing merge, create one immutable tag for the exact commit and deploy its source together with its matching `public/assets/build/` output through the shared installer; provide a manual dispatch for an already-published tag using that same installer. Reject unknown tags or missing/mismatched build output before host mutation. Keep the existing deployment target, production Composer install, and forward-only Phinx migrations; do not add migration rollback. Store access values in protected settings or host-local configuration and keep them out of tracked files, release payloads, and logs. Document required branch-protection checks and operator use. **Acceptance:** PR workflow runs each required check and a controlled failure fails the workflow. A successful merge tags the triggering commit and deploys its corresponding source/build pair without invoking Node on the host. Manual selection deploys a published tag's matching source/build pair through the same installer; invalid or unavailable releases fail before server mutation. Installer failures propagate as failures, existing host-local configuration and production data remain intact, and migrations are forward-only. Workflow syntax, docs, package contents, and changed files contain no real or identifying infrastructure values. Repository branch protection is verified before reporting that failed checks block merges. **TDD/characterization:** Add or extend focused checks for release package tag/source/build identity and exclusions; valid and invalid selected releases; rejection before mutation; preservation of host-local configuration/data; and installer failure propagation. Check workflow syntax and event/ref selection, then exercise the deployment path against an isolated fixture or staging target, including asset loading where available. **Gate:** Focused release-package and installer checks, shell syntax/static checks, workflow syntax validation, all configured PR commands (`composer test`, `npm --prefix frontend ci`, `npm --prefix frontend run test`, and `npm --prefix frontend run build`), package/tag identity and failure-path checks, and infrastructure disclosure audit. At Review, verify branch protection and the integrated staging or isolated deployment behavior; do not deploy to production as part of this task. **Dependencies:** none.

**Code-stage decision:** On 2026-10-20, Paulo Bezerra approved semantic release tags selected by one `patch`, `minor`, or `major` PR label. After merge to `main`, the workflow computes the next `vMAJOR.MINOR.PATCH`, creates the tag and GitHub release, and deploys the matching package. The first release uses `v0.0.0` as a calculation baseline when no SemVer tag exists; existing `release-*` tags remain available for redeployment. The version is derived from Git tags rather than hard-coded in `composer.json`.
