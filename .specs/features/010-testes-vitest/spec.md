# SPEC — Fast frontend tests without a browser

**ID:** 010-testes-vitest · **Status:** proposed · **Date:** 2026-10-20

**User validation for Plan:** Paulo Bezerra approved this Spec by saying “concluir” on 2026-10-20.

## Problem, baseline, and goal

The existing frontend test command runs `frontend/tests/build-check.mjs` before Vitest. That script performs a Vite production build, and `frontend/tests/integration.test.js` then starts Chromium through Playwright and exercises the live PHP application. `tools/test-frontend.sh` delegates to that command, while `tools/test-all.sh` also invokes PHPUnit through Docker Compose. In GitHub Actions, the PHP test job starts MySQL, applies migrations, writes a placeholder Vite manifest, and then runs PHPUnit. These checks mix product behavior with browser, build, database, and environment setup.

The user requires fast Vitest tests that mock external dependencies, never launch a browser or application service, and finish within 20 seconds per frontend and backend suite. The reusable PHP/Vue skeleton should retain tests that demonstrate application behavior and remove redundant or infrastructure-only tests and wrappers.

## Scope and constraints

- **Included:** Replace the Playwright frontend suite with browserless Vitest component and client tests; mock API, persistence, and other external boundaries; remove test-only browser/build checks and redundant shell wrappers; reduce PHPUnit coverage to valuable application behavior that runs without Docker or external services; simplify the pull-request test workflow; update permanent project Markdown guidance that contradicts the Vite build or new test commands.
- **Out of scope:** Changing application behavior, API contracts, database schema, production build output, release packaging, deployment behavior, or historical Feature/Spec/Plan/Review/Bug records. In particular, do not edit older feature records that contain the former no-build decision.
- **Constraints:** Keep the Vue 3/Vite frontend and native PHP/Apache deployment. Vitest remains the frontend test runner. Do not use Playwright, Chromium, a live PHP server, MySQL, Docker Compose, or real network services for the default test suites. Do not add a custom test framework. Each full frontend and backend test command must complete within 20 seconds. Preserve the separate production Vite build check.

## Technical solution

**Technical decision:** Use Vitest with Vue Test Utils v2 and `happy-dom` to mount only components whose user-visible behavior adds value. Mock the API and other external dependencies at their module boundaries with Vitest. Keep PHPUnit for domain, application, and in-process HTTP behavior using repository and service test doubles. No default test suite starts an external service or container.

No real technical alternative remains: the Feature and the user's clarification explicitly require Vitest and browserless, mocked tests. Plain Node's built-in test runner does not meet that decision. A real browser or live-service test also conflicts with the required runtime and duration limits. Vue documents Vue Test Utils as its component test utility and recommends it for Vue applications; its Vue 3 edition supports mounting components in isolation. Vitest provides module and function mocks. References: [Vue testing guide](https://vuejs.org/guide/scaling-up/testing.html), [Vue Test Utils](https://test-utils.vuejs.org/guide/), and [Vitest mocking](https://vitest.dev/guide/mocking.html).

**Reason for the decision:** This keeps the requested Vitest runner, tests actual Vue component behavior in a simulated DOM, and avoids waiting for Chromium, PHP/Apache, MySQL, migrations, or Docker. Vue's testing guide documents `happy-dom` with Vitest and recommends Vue Test Utils for Vue components. These are test-only dependencies; exact versions must be checked for compatibility with the locked Vue, Vite, Vitest, and Node versions before adding them. Direct module mocks are sufficient for this scope; do not add a request-mocking server or another test framework without evidence that it is necessary.

**CI tooling decision:** Keep the existing maintained runtime setup actions (`shivammathur/setup-php` and `actions/setup-node`) and run the repository's Composer and npm test commands directly. Do not add a third-party action merely to invoke PHPUnit or Vitest, and do not call project `.sh` test wrappers from GitHub Actions. `actions/setup-node` already provisions Node and can cache npm data; `setup-php` provisions PHP and Composer. A generic action cannot replace the project's own assertions or remove the need to invoke its test commands. The current `tools/test-all.sh` is a local wrapper, not called by the workflow; the workflow's MySQL service, migration, and placeholder-manifest steps are the unnecessary test setup to remove. Keep the bespoke release/deployment steps outside this Spec.

**Recorded project-policy correction:** `AGENTS.md`, `.specs/project-context.md`, and `.specs/implementation.md` still prohibit Node/npm/build steps and describe the former build-free frontend. The user stated on 2026-10-20 that this prohibition should have been removed several Features earlier and explicitly requested correcting permanent project Markdown documents. Treat those statements as approval to correct permanent guidance in Code. Do not change old Feature records, including `.specs/features/008-menu-lateral-recolhivel/` and `.specs/features/009-deploy-producao/`.

## Requirements

- **S010-01 — Frontend behavior coverage:** The frontend test command runs Vitest only, without a Vite production build, browser, live application, real network, or external service. Tests use a simulated DOM only for selected Vue interactions and mock the API boundary. Retain useful checks for authentication form outcomes, auth-state changes, and the API client's locale/CSRF behavior. Remove layout/computed-style checks, static home-page or technology-mark checks, shell/manifest checks, and other assertions that only verify build or browser infrastructure. **Verification:** inspect test imports and setup for Playwright/browser/server/network usage; run the frontend test command and confirm it passes within 20 seconds.
- **S010-02 — Minimal frontend test tooling:** Vitest remains the only runner; use Vue Test Utils v2 and one compatible DOM simulator only where mounting a Vue component is needed. Remove Playwright and its lockfile entries, and remove the production-build invocation from the test script. Keep the production build as its existing separate quality check. **Verification:** inspect `package.json`, lockfile, Vitest config, and test imports; run the frontend tests and the separate production build.
- **S010-03 — Backend suite without services:** The default PHPUnit suite runs without Docker, MySQL, migrations, a live web server, or network access. Mock repository/service boundaries for behavior tests. Remove or replace database-backed tests that require a service, including the current persistence/schema and full lifecycle cases in `AuthPersistenceTest`, `CmsPersistenceTest`, and `PostOwnershipTest`, and the database-boot case in `EnvironmentConfigurationTest`. Keep focused tests for domain invariants, authentication, authorization/ownership, CSRF/session behavior, safe Markdown rendering, and meaningful HTTP contracts when they run in process with external dependencies replaced. Remove tests that only assert obsolete routes, source text, generated-manifest plumbing, or other implementation/deployment setup without protecting a maintained contract. **Verification:** run the complete PHPUnit suite with Docker unavailable and no database environment; confirm it passes within 20 seconds and that retained security/business behavior remains covered.
- **S010-04 — No unnecessary test orchestration:** Remove `tools/test-frontend.sh` and `tools/test-all.sh`; the npm and Composer commands are sufficient locally and in CI. The GitHub test workflow runs the package commands directly, uses standard setup actions, and does not start MySQL, apply migrations, generate placeholder assets, or call a shell wrapper. Enforce a 20-second limit on each test step. **Verification:** inspect workflow steps and repository references; confirm frontend and PHP tests are separate timed steps and no test job declares a database/container service.
- **S010-05 — Permanent guidance matches the project:** Correct permanent Markdown documents that claim the frontend has no build or forbid Node/npm/Vite, and update their local test instructions to remove browser, active-app, Docker, or obsolete wrapper requirements. The initial scope includes `AGENTS.md`, `.specs/project-context.md`, `.specs/implementation.md`, and `README.md`; update other permanent Markdown only where a contradictory statement exists. Do not edit historical feature artifacts. Update localized home-page quality guidance if it still describes the removed browser suite or wrapper. **Verification:** search permanent Markdown and active contributor guidance for no-build/no-Node prohibitions and obsolete browser/test-all instructions; confirm any remaining references are accurate and feature history is untouched.
- **S010-06 — Preserve production delivery:** The separate production Vite build and release/deployment workflow continue to build and publish the same assets. No PHP/API/database contract or production behavior changes. **Verification:** run the production frontend build and inspect the workflow diff to confirm release/deployment steps and asset paths are unchanged.

## Contracts, data, and security

The frontend suite uses Vitest with simulated DOM APIs and mocked HTTP/API dependencies; it must not make real requests. Backend tests use in-process requests or direct service calls with repository doubles and leave persistent state unchanged. The default test commands require no `.env`, session service, database, Docker daemon, browser, or running application. Security behavior remains under test at the layer that owns it: frontend tests verify request headers/CSRF retry and auth-state handling, while PHP tests verify backend authorization, CSRF, session, password, and Markdown-rendering rules. No schema migration, route, payload, or HTTP status change is part of this work.

## Acceptance and verification criteria

- **Frontend success:** Given installed frontend dependencies, when the documented frontend test command runs, then Vitest exercises selected Vue/API behavior with mocked external boundaries, starts no browser or application service, and completes within 20 seconds. Test: `npm --prefix frontend run test` under a 20-second limit.
- **Backend success:** Given installed PHP dependencies and no Docker/database service, when the documented backend test command runs, then the retained PHPUnit suite verifies core application and security behavior and completes within 20 seconds. Test: `composer test` under a 20-second limit with Docker unavailable and database variables unset.
- **CI:** On a pull request, frontend and PHP test steps run with the standard runtime setup actions and fail if either test command exceeds 20 seconds. No MySQL service, migration, placeholder manifest, or test wrapper is required. Test: inspect workflow and run the equivalent commands on the CI runner.
- **Production compatibility:** Given the same frontend source and locked dependencies, when the separate production build runs, then the manifest and assets remain emitted under `public/assets/build/` and the release/deployment pipeline continues to consume them. Test: `npm --prefix frontend run build` and inspect generated paths/workflow inputs.
- **Documentation:** Active permanent project guidance describes the Vite build and service-free test commands consistently; historical feature records remain unchanged. Test: targeted search of permanent Markdown and Git diff review.

**Applicable gate:** During Code, run the frontend and backend suites separately, enforcing the 20-second limit for each; run the separate production frontend build because the workflow must preserve production assets. No Docker/browser/E2E check applies. At Review, rerun the two test suites and production build only if changes or concrete risk justify it. No tests were run during Spec.
