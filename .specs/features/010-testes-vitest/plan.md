# PLAN — Fast frontend tests without a browser

**Feature:** [feature.md](feature.md) · **Spec:** [spec.md](spec.md) · **Date:** 2026-10-20 · **Status:** open

**User validation to start Code:** Paulo Bezerra approved this Plan by saying “aprova o plano” on 2026-10-20.

## Delivery strategy

Deliver the work in three dependent increments. First establish valuable browserless Vitest coverage and remove the browser/build checks that currently prevent the frontend suite from meeting its contract. Next retain the valuable PHP behavior and security tests while removing database/service-dependent cases from the default suite. Finally align local commands, CI, and active project guidance with those suites, then verify the separate production build and release workflow. No task changes application behavior, API contracts, schema, or deployment behavior.

## Risks and final verification

The principal integration risk is removing MySQL setup from a workflow that currently shares test and production-build jobs; confirm release/deployment jobs retain their existing dependency and asset paths. Recheck that default test commands use mocks or in-process doubles and that mock coverage does not replace the security and application behavior required by S010-01 and S010-03. Validate the production Vite build separately because the test command will no longer build assets. No migration, API, browser, or live-service integration check applies to this feature.

**User-authorized scope exception (2026-10-20, Paulo Bezerra):** The user expressly authorized evaluating and changing deployment tooling to remove manual `.sh` scripts, with the condition that a replacement should be adopted only if it reduces overall complexity; if complexity increases, retain the current process. This overrides the Spec's deployment-tool exclusion for this evaluation. The assessment found 247 lines in the two deployment scripts, plus deployment-specific workflow commands. The available GitHub Marketplace SSH/rsync actions cover file transfer and remote command execution, but not this project's package metadata and Vite-manifest validation, `.env` preservation, Composer install, and Phinx migration. Deployer could own deployment orchestration, but still needs project-specific recipes and package validation and adds a Composer dependency and deployment model/configuration. This is not a reduction to a small declarative configuration and would increase the maintained toolchain and operational concepts. Therefore this Feature keeps the current, actively used deployment scripts and behavior; no deployment migration is planned. Reconsider only if a later option demonstrates a net complexity reduction while preserving the package and deployment guarantees.
