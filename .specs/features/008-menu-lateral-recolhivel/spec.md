# SPEC — Collapsible sidebar menu

**ID:** 008-menu-lateral-recolhivel · **Status:** proposed · **Date:** 2026-10-19

**User validation for Plan:** validated. **Statement:** "validar spec". **Name:** Paulo Bezerra · **Date:** 2026-10-19.

## Problem, baseline, and goal

The application shell in `src/template/index.phtml` renders the sidebar permanently. `public/assets/css/app.css` gives it a fixed 240px desktop width and stacks it above the page on narrow screens. The current SPA is made of native ES modules in `public/assets/js/`, with Vue 3.5.13 and Vue Router 4.5.0 loaded as globals from `public/assets/vendor/`. The user-validated Feature asks for the sidebar to start hidden, with hamburger and close controls, so the current page can use the available screen space.

## Scope and constraints

- **Included:** hidden initial sidebar state; accessible hamburger and close controls; responsive layout; Lucide Vue icons; establish a Vite/Tailwind frontend development/build workflow; configure shadcn-vue and use its Sidebar components; move the SPA source to Vue Single-File Components; document the selected frontend technologies on the home page alongside the existing technology marks.
- **Out of scope:** changing navigation destinations or route definitions; changing authentication or authorization; API contract, database, or migration changes; moving or reorganizing the existing PHP backend source tree.
- **Constraints:** PHP continues to serve the application shell and API at the same origin. Node/npm are development/build tools only; production serves compiled assets from `public/` through PHP/Apache and does not require Node. Keep generated output within the public assets directory and keep frontend source outside the document root. This explicitly supersedes the Feature's no-build product constraint for the frontend workflow; the Feature remains unchanged.

## Technical solution

**Technical decision:** use Vite for frontend development and production builds, with the SPA source in `frontend/src/spa/` and its API client modules in `frontend/src/api/`. Keep the PHP application under its existing `src/` tree; this avoids conflating PHP backend code with browser code or moving backend files. Convert the SPA entry, router, and page/component views to `.vue` Single-File Components as needed to preserve existing behavior. Configure Tailwind CSS v4 through its official Vite plugin and configure shadcn-vue for JavaScript components (no TypeScript migration). Use the shadcn-vue Sidebar component set as the shell sidebar foundation, with `defaultOpen=false`, no persisted open state, and off-canvas collapse behavior; use its trigger/controlled state for the hamburger and close controls. Import `Menu` and `X` icons from Lucide's Vue package, bundled with the app. shadcn-vue components are project source generated/copied into the repository and remain customizable; they are not delivered from a production CDN. Pin package versions through `package.json` and its committed lockfile. Vite development mode serves transformed modules and HMR on its own local port while PHP continues serving the shell and API; configure Vite CORS to allow only the local PHP origin and make the development CSP permit the Vite client and HMR WebSocket. Frontend API calls remain relative to the PHP origin, so they do not require API CORS changes.

In production, `npm run build` emits hashed JavaScript and CSS assets plus a Vite manifest under `public/assets/build/`. `src/template/index.phtml` uses the Vite dev-server entry only in development; otherwise it resolves the built entry and styles from the manifest. Apache/PHP remains the production server and no Node runtime is installed or invoked for requests. Keep the build directory generated from source and publish it through the project's normal image/assets workflow. Tailwind CSS, Vue, Vue Router, Lucide icons, and the runtime dependencies used by generated shadcn-vue components are included in the compiled assets; production has no frontend CDN dependency. Remove the old global Vue and Vue Router distributions and their script references. Keep the existing app CSS for legacy page styles during this feature; apply Tailwind/shadcn-vue to the shell and sidebar without requiring a wholesale redesign of existing pages.

Update the home page's existing technology-mark section with linked marks for Vite, Tailwind CSS, shadcn-vue, and Lucide, pointing to each project's official documentation. Keep the marks local to the application assets and provide visible names plus meaningful image alternatives. Update the localized English and Brazilian Portuguese homepage copy that currently describes a build-free frontend so it accurately explains the Vite development/build flow, the Vue/Tailwind/shadcn-vue/Lucide stack, and the production assets served from `public/`. Document the exact commands `npm --prefix frontend ci`, `npm --prefix frontend run dev`, `npm --prefix frontend run build`, and `npm --prefix frontend run test`, including that the PHP app must also be running for same-origin API access and that the build must run before building/deploying the production PHP image. Add a corresponding frontend development/build/test section to the root README with the same commands and responsibilities. Do not turn the home page into full third-party documentation; the technology marks link to canonical docs and the surrounding stack/build explanation summarizes this project's usage.

Move the sidebar visibility state into the SPA shell component and initialize it to `false`. Keep the sidebar and controls in the existing PHP base template or its Vue shell component, according to the current mount boundary. Add an always-available localized hamburger button outside the sidebar and a close button inside it. Both use native button semantics, localized accessible names, `aria-expanded`, and `aria-controls`; the icon glyphs are decorative. Hide the closed sidebar so page content uses its space. Preserve the existing stacked layout when the sidebar is open at narrow widths. Keep existing navigation links, route definitions, and auth-based visibility unchanged. Update the vendor guidance so it no longer claims the Vue libraries are stored locally.

**Reason for the decision:** the user accepted the Vite model where Node serves/transforms assets during development and builds the frontend into `public/` for production, then specified separated API/SPA source and `.vue` files, and chose Lucide, Tailwind, and shadcn-vue as the frontend UI stack. `frontend/src/{api,spa}` gives browser code a clear boundary while leaving the established PHP architecture intact. shadcn-vue provides a maintained Vue sidebar foundation and copies customizable component source into the repository; Tailwind and Lucide integrate into the same Vite build. PHP continues to serve both the shell and API, preserving same-origin API requests and avoiding changes to API CORS. The build adds a manifest lookup and development-only CSP/CORS configuration; production remains a single PHP/Apache deployment. This explicitly replaces the Feature's no-build constraint, the previous Tabler CDN selection, and the earlier decision to serve Vue and Vue Router from CDN URLs. The earlier general CDN preference is superseded for the frontend libraries bundled by this build. No database or API contract changes apply. Official references: [Vite backend integration](https://vite.dev/guide/backend-integration.html), [Vite server CORS](https://vite.dev/config/server-options.html#server-cors), [Tailwind CSS with Vite](https://tailwindcss.com/docs/installation/using-vite), [shadcn-vue manual installation](https://www.shadcn-vue.com/docs/installation/manual), [shadcn-vue Sidebar](https://www.shadcn-vue.com/docs/components/sidebar), and [Lucide Vue package](https://lucide.dev/packages).

## Contracts, data, and security

There are no HTTP, authentication, session, CSRF, persistence, or migration contract changes. Existing route links and auth-based link visibility remain intact. Sidebar visibility is transient client-side presentation state and resets to hidden on a full page load. Both controls are native buttons with `type="button"`, localized accessible names, `aria-expanded` reflecting current visibility, and `aria-controls` referencing the sidebar element. Icons are decorative to assistive technology because the buttons provide their names.

The base template will load development assets from the local Vite server only in development and production assets from the manifest under `public/assets/build/`. The production PHP/Apache runtime does not need Node/npm and does not depend on a frontend CDN. Vue, Vue Router, Tailwind, Lucide, and the runtime dependencies used by shadcn-vue components are included in the frontend build. Development CSP and Vite CORS must permit only the local PHP origin, Vite module origin, and HMR WebSocket needed by the configured local ports. API requests continue to use relative same-origin paths with credentials. No backend API CORS policy or response contract changes.

## Acceptance and verification criteria

- **Success:** given a fresh PHP-served page with built assets at desktop width, when the shell initializes, then manifest-resolved Vue/Tailwind assets load, the shadcn-vue Sidebar starts closed, the content uses the available width, and the Lucide hamburger trigger is exposed as collapsed. Activating hamburger and then close shows and hides the sidebar, with `aria-expanded` updating each time. Test: build then run `npm --prefix frontend run test` against PHP; inspect output URLs, layout, and accessibility attributes.
- **Development boundary:** with PHP and Vite active, opening the PHP origin uses Vite modules/HMR and calls `/api/*` on that same PHP origin. Vite CORS and CSP allow only configured development endpoints. Test: browser network inspection for module/HMR requests and API origin.
- **Failure/boundary:** if the Vite manifest is absent in production, the template must fail clearly rather than request development assets or deleted vendor files. Lucide icons are part of the bundle, so an icon cannot independently fail due to CDN availability; accessible button names remain in the rendered markup. Test: exercise the production template with a valid build manifest and validate the missing-manifest failure path at template level.
- **Integration/compatibility:** given anonymous and authenticated sessions at wide and narrow viewport widths, when the sidebar is opened, then the same route links and auth-dependent items appear and navigate as before. The home page and README display matching, working official documentation links and accurate stack/build/test instructions, including the npm commands and Docker production build order. Test: run Vitest browser tests across `/`, `/blog`, `/login`, and authenticated `/my-posts`; confirm no API or route changes, no production frontend CDN requests, and working documentation links in both locales; compare README commands to the home copy.

**Applicable gate:** browser end-to-end coverage is required because the change affects SPA bootstrap, Vite integration, shadcn-vue sidebar interaction, and responsive layout. During Code, run `npm --prefix frontend run test` against the active PHP app with the configured Playwright Chromium available; at Review, run `./tools/test-all.sh` if the environment supports it.
