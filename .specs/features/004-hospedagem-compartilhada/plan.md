## Delivery strategy

T004-01 makes the existing ignored `.env` a usable fallback for both web startup and Phinx, while keeping process variables authoritative for Compose. T004-02 delivers the complete shared-hosting installer in one increment: update remote `main`, install production dependencies, and run pending migrations. The installer cannot report a successful deployment before all three steps finish. No task changes routes, frontend, Docker commands, or migration definitions.

Each increment must update the project's operator documentation in `README.md` for the behavior it delivers. The completed feature must leave one usable shared-hosting procedure there, with commands and failure recovery consistent with the implemented configuration loader and installer.

## Risks and final verification

Configuration requires a real startup/route check and a Phinx read against disposable MySQL; unit parsing alone does not establish deployment viability. The `.env` syntax must agree for documented Compose and PHP cases, and the web root must actually be `public/` so secrets stay outside HTTP access. The installer modifies code and schema in place: test only with temporary Git checkouts and disposable databases, including repeat migration and privilege failure. A failed Composer install or migration after pull leaves a partial deployment; nonzero output and recovery instructions are part of acceptance. New migration files and database/user provisioning remain outside this feature.

All seven Spec requirements map to an acceptance check in the tasks. Before T004-02, verify T004-01 through its checklist, diff, code, and tests; a checkbox alone is insufficient. Code marks only its task complete after its acceptance and gates pass. Do not create per-task execution records.
