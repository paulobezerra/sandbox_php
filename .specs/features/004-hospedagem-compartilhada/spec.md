# SPEC — Production configuration for shared hosting

**ID:** 004-hospedagem-compartilhada · **Status:** proposed · **Date:** 2026-10-17

**User validation for Plan:** validated. **Statement:** "aprova essa birosca". **Name:** Paulo Bezerra · **Date:** 2026-10-17.

## Problem, baseline, and goal

On shared PHP hosting, the application may receive no database variables from the host. `Config::fromEnvironment()` currently reads only `getenv()`, so missing `DB_DATABASE` or `DB_USERNAME` stops startup. Both the web application (`src/Bootstrap/App.php`) and Phinx (`phinx.php`) use this method. Application startup also opens a PDO connection, so correct values must reach PHP before it can serve a route.

The repository already has a Git-ignored `.env` and a versioned `.env.example`. Docker Compose reads `.env` and passes settings to PHP, but PHP itself does not read the file. The production Docker image excludes `.env` and receives its settings from Compose. The README currently tells shared-hosting operators to configure PHP environment variables through their provider.

The operator must be able to use the existing private `.env` in the project root for shared-hosting production settings. The same PHP configuration path must serve web requests and Phinx, while variables already supplied by Docker Compose retain priority. The updated validated Feature calls for one non-interactive installer that updates the local `main` checkout from remote `main`, installs dependencies, and applies pending migrations.

Phinx already uses `Config::fromEnvironment()` and its `DB_USERNAME`/`DB_PASSWORD` in both configured environments. The current migration creates `users`, `posts`, indexes, and a foreign key; Phinx also maintains its tracking table within the configured database. Neither creates a database or a MySQL account. MySQL root appears only in the Docker MySQL service's initialization and health check, not in application or Phinx credentials. A shared host therefore needs an existing database and an assigned user with schema-change privileges on that database, not MySQL root access. Whether a particular hosting account grants those privileges remains an operational prerequisite to verify.

## Scope and constraints

- **Included:** read the existing project-root `.env` as a configuration fallback, preserve process-environment precedence, diagnose missing or malformed configuration without disclosing secrets, document the shared-hosting layout and settings, and provide an installer that pulls `main`, installs production dependencies, and applies pending existing migrations.
- **Out of scope:** a second private configuration file; provider-managed environment setup; automating account creation, SSH access, GitHub configuration, database/user provisioning, or authoring new migrations; changing business behavior, HTTP contracts, or Docker-based deployment commands.
- **Constraints:** PHP 8.4, Composer 2, `public/` as the web root, secrets outside `public/` and version control, and the existing Phinx migration mechanism. The installer must be usable by future SSH automation without interactive input and must not require MySQL root. A repository-pinned Composer PHAR is used only by the shared-hosting installer; Docker keeps its current Composer source.

## Technical solution

**Technical decision:** On 2026-10-16, after rejecting the separate PHP file design, the user explicitly selected reading the existing `.env`. Use a standard dotenv parser as a production dependency and read the file into an array without writing to process-global environment variables. Merge the parsed values with the existing `getenv()` values, giving each process value precedence, then pass the result through `Config::fromArray()` and its existing validation. Both the app and Phinx already call `Config::fromEnvironment()`, so one change there serves both.

**Chosen option — existing `.env` with `vlucas/phpdotenv`, moderate code impact.** Update the Composer manifest and lock file, `src/Bootstrap/Config.php`, configuration tests, README, and the update helper in `tools/`. `vlucas/phpdotenv` 5.7 supports PHP 8.4 and provides array-backed loading, allowing PHP to parse quoted values and comments without `putenv()` or mutations to `$_ENV`/`$_SERVER`. Its cost is a runtime dependency and the need to document/test a `.env` syntax shared with Compose. The existing `.env` and `.env.example` remain the only configuration files. [Package requirements](https://packagist.org/packages/vlucas/phpdotenv), [array-backed loading and syntax](https://github.com/phpdotenv/phpdotenv#parsing-without-loading).

**Alternative — parse `.env` with project code, moderate code impact, rejected.** This avoids a dependency but makes this project responsible for quoting, comments, empty values, interpolation, and passwords containing special characters. A small parser would either duplicate maintained library behavior or support a narrower format than operators may already use with Compose. It increases maintenance and the risk of silently changing secrets.

**Alternative — separate private PHP configuration file, moderate code impact, rejected by the user.** This would avoid a parser dependency, but it requires operators to maintain a second production configuration format alongside the existing `.env`. It was the earlier Spec decision and does not match the user's chosen process.

**Reason for the decision:** reusing `.env` gives shared-hosting operators the same source file already documented for Compose, without provider-specific setup. The maintained parser handles real dotenv syntax, while array-backed loading keeps the application independent of whether PHP populates `$_ENV` on a shared host. Process-environment precedence preserves current Docker settings. The configuration change itself needs no new database migration or API change. Only recognized application keys flow into `Config::fromArray()`; Compose-only keys such as `DB_ROOT_PASSWORD` and `APP_PORT` remain outside the PHP configuration contract.

For deployment, `tools/deploy-shared-hosting.sh` locates its checkout, verifies a clean local `main`, checks Git and a PHP CLI compatible with `^8.4`, then fast-forward pulls remote `main`, runs `composer install` with production options under that PHP, and runs pending Phinx migrations in the production environment under the same PHP. With no override, Git is the `git` executable found on `PATH`; Composer is the versioned project-root `composer.phar` run under the selected PHP. The operator may set `PHP_BIN` and `GIT_BIN` in the existing `.env` if those tools are outside `PATH`, and `COMPOSER_BIN` only when deliberately using a different Composer entry point. Explicit process values override file values. No provider-specific binary path is hard-coded. It relies on existing Git credentials, the existing database, and its assigned `DB_USERNAME` account; it does not configure GitHub, SSH, a database, or MySQL root. This in-place sequence can leave a partial deployment if dependency installation or migration fails after the pull. It must stop immediately with a nonzero result, identify the failed step, and never claim successful deployment or attempt an automatic rollback.

**Composer distribution choice — versioned PHAR, low code impact and one binary artifact.** A verified official Composer 2 release is committed at the project root as `composer.phar`; the currently ignored local file is not assumed to be trusted or suitable for committing. This makes shared-hosting installation independent of a host-level Composer command and ties the installer to the project's reviewed release. To change Composer versions, verify a new official PHAR and replace it in a normal repository commit; the next `git pull` brings that version to the host. Never run `self-update` in production, since modifying the tracked PHAR would dirty the checkout and evade release review. Composer documents local PHAR execution, exact release downloads with checksums/signatures, and `self-update` behavior. [Official download](https://getcomposer.org/download/), [official CLI documentation](https://getcomposer.org/doc/03-cli.md).

**Alternative — host-installed Composer on `PATH`, low code impact, not selected as the default.** This avoids a binary in Git but makes availability and version depend on each host. Keep `COMPOSER_BIN` as an explicit override for an operator who manages Composer separately; verify that the chosen entry point runs under the selected PHP and is Composer 2. The existing Docker images continue using their own Composer binary, so this choice does not change their build process.

## Requirements

- **S004-01 — Shared-hosting fallback.** Given a readable, valid project-root `.env` and no required process variables, when the web application or Phinx loads configuration, it uses the file's application settings. With a reachable configured database, application startup connects and an existing route is served.
- **S004-02 — Environment precedence.** Given the same recognized key in `.env` and the process environment, the process value wins for that key, including an explicitly empty value, and other keys may come from `.env`. Existing `Config::fromArray()` validation runs on the merged result.
- **S004-03 — Safe failures.** An absent `.env` leaves environment-only configuration working. An unreadable or malformed present file, or missing/invalid effective required settings, stops initialization with an operator-useful diagnostic that names the file or key without printing secret values or raw configuration lines.
- **S004-04 — Portable guidance.** The README shows how to copy the existing `.env.example` to the ignored `.env`, set unique credentials, production mode, disabled debug/OpenAPI, and a public HTTPS `APP_URL`, keep the file outside `public/`, point the web root at `public/`, and diagnose configuration errors. It documents optional `PHP_BIN` and `GIT_BIN`, the versioned Composer PHAR default and optional `COMPOSER_BIN` override, how a verified Composer release is updated through Git, installer invocation, backup before deployment, an existing database and user with the needed schema privileges, and recovery from a partial deployment. `DB_ROOT_PASSWORD` is Docker-only and is not needed on shared hosting.
- **S004-05 — Docker compatibility.** When Compose supplies application variables, those values continue to determine configuration even if a development bind mount also contains `.env`. Production Docker still works without a `.env` inside its image. No Compose command or environment contract changes.
- **S004-06 — Production installer.** Given a clean local `main` checkout with accessible remote `main`, usable Git and PHP `^8.4`, the versioned Composer PHAR, and a configured database, invoking the installer from any working directory selects Git and PHP from their process overrides, then `.env` values, then `PATH` (where Git defaults to `git`); it selects Composer from a process `COMPOSER_BIN`, then `.env` `COMPOSER_BIN`, then the project-root `composer.phar`. It fast-forward pulls remote `main`, installs production dependencies under the selected PHP, then applies pending Phinx migrations under that PHP using the production environment. An invalid configured path, incompatible PHP, missing/invalid PHAR, or incompatible Composer 2 entry point fails instead of silently choosing another executable. It returns zero only when all three deployment steps succeed. Missing or incompatible tools, a dirty or wrong-branch checkout, inaccessible remote/authentication, divergence, pull failure, Composer failure, or migration failure returns nonzero with the failed step identified. It does not prompt, switch branches, downgrade code, or automatically roll back, so future SSH automation can inspect its exit status and output. Repeating the invocation with no new changes is safe.
- **S004-07 — Rootless database migrations.** Given an existing database and `DB_USERNAME`/`DB_PASSWORD` with sufficient schema privileges on it, Phinx creates/updates its tracking table and applies pending migrations as that configured user. The installer never reads `DB_ROOT_PASSWORD` or connects as MySQL root. If the assigned user lacks required privileges, migration failure is reported as a deployment failure without substituting root credentials or continuing to success.

## Contracts, data, and security

The only file source is the existing `.env` at the application root, outside `public/`. It remains ignored by Git and excluded from the production Docker image. Parse it into an isolated array; do not use unsafe dotenv modes or `putenv()` to alter global process state. Read the same recognized keys already handled by `Config::fromEnvironment()`, including database, application, session, and locale settings. Merge by key with `getenv()` values taking precedence; treat a process value of the empty string as present so existing validation can reject it. Ignore Compose-only keys in PHP. Keep current defaults and validation in `Config::fromArray()`.

Support the documented shared subset of dotenv and Compose syntax, including comments and quoted values containing `#`, `$`, or `=`. Document quoting where necessary and verify representative secrets produce the same effective application values in PHP and Compose. Never include `.env` contents or raw parser exception text in HTTP responses, logs, or command output. A missing file is allowed when environment settings suffice; a present unreadable or malformed file is an error rather than an empty fallback.

The installer resolves the repository from its own path and requires a clean working tree on local `main`; the ignored `.env` does not make the checkout dirty. It requires the branch's configured upstream to be remote `main` and pulls it with fast-forward only, without assuming a remote name such as `origin` or configuring one. For `PHP_BIN` and `GIT_BIN`, use the process-environment value first, then its literal assignment in the project-root `.env`, then a compatible executable on `PATH`. For `COMPOSER_BIN`, use the process value first, then the file value, then the repository's tracked `composer.phar`; a missing/invalid default PHAR is an error, not a silent fallback to host Composer. Do not source or evaluate `.env` as shell code. Document optional binary settings as absolute paths without interpolation or shell syntax; for example, `PHP_BIN=/opt/cpanel/ea-php84/root/usr/bin/php` is a value an operator can place in their own `.env`, not a candidate embedded in the script. A present but invalid configured value fails with a useful diagnostic. The PHP configuration loader ignores these installer-only keys. Run Composer and Phinx under the selected PHP even if the default `php` is older; verify the chosen Composer entry point can run under that interpreter and reports Composer 2. Git, Composer, and Phinx must fail rather than request interactive input. Install without development dependencies and with an optimized autoloader. After a successful install, run only pending Phinx migrations using the production environment. A migration failure stops the installer and reports the partial update; no rollback is attempted.

During Code, replace the existing `.gitignore` rule for root `composer.phar` so the reviewed PHAR is tracked, while keeping `.dockerignore` exclusion so Docker's current Composer source is unchanged. Obtain the PHAR from an official pinned release and verify its published digest/signature before adding it. The installer must not download or self-update Composer on the server. No Composer binary or ignore rule is changed during this Spec step.

The same `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, and `DB_PASSWORD` used by the application feed Phinx. The operator creates the database and account through the host's supported process before deploying. The assigned account needs access to the configured database and enough DDL/DML privileges for the existing schema and Phinx's tracking table: creating and altering tables, indexes, and foreign keys, plus reading/writing migration metadata. Future migrations may require additional privileges, which must be checked before rollout. No root account, `CREATE DATABASE`, `CREATE USER`, or global privileges are required by the current application or migration. Docker's separate `DB_ROOT_PASSWORD` is for the containerized MySQL service only and remains outside the shared-hosting PHP contract.

There are no route, payload, authentication, new schema definition, or OpenAPI/SPA changes. Deployment now executes existing pending migrations, so a backup and privilege check precede production invocation. The old Plan still describes a second PHP configuration file and omits installer migrations; it must be regenerated in a separate Plan step after this revised Spec is validated, rather than silently used for Code.

## Acceptance and verification criteria

- **Configuration success:** with required process variables absent and a valid `.env`, both the web bootstrap and Phinx read its settings; with a test database, startup connects and serves an existing route. Verify at unit and integration levels without real production credentials.
- **Precedence and syntax:** with a key in both sources, the process value wins; file-only keys fill gaps. Verify quoted special characters, comments, empty values, and relevant Compose/PHP parity with representative test data.
- **Configuration failure:** absent `.env` plus complete process environment succeeds; absent required settings, an unreadable file, malformed syntax, or an invalid effective value fails with a safe diagnostic and no secret value. Verify error output and absence of raw file lines.
- **Deployment compatibility:** development and production Compose process variables retain priority, production Docker does not require a copied `.env`, and the README keeps secrets outside `public/`. Review the documented layout and configuration behavior.
- **Installer:** use a temporary repository and substitute executables to verify Git's `git` default, each binary's `.env` value and process override precedence, compatible PHP detection on `PATH`, the tracked Composer PHAR default, invalid-path/version or missing-PHAR failure, safe handling of shell metacharacters in `.env`, correct PHP for Composer and Phinx, local/remote `main` enforcement, fast-forward only, non-interactive exit status/output, step ordering, repeat invocation, failures before later steps, and invocation from outside the checkout. Confirm the PHAR is tracked, sourced from a verified official release, and excluded from Docker's build context. No production checkout is touched.
- **Migration integration:** with a disposable database and a non-root user granted database-scoped schema privileges, run the installer against an initial schema and again with no pending migrations; verify `users`, `posts`, and `phinxlog` and zero exit status. Revoke a required schema privilege in a separate disposable test and verify nonzero exit, an identified migration failure, and no success claim. Confirm Phinx uses `DB_USERNAME`, not `DB_ROOT_PASSWORD`. Do not test against production data.

**Applicable gate for later Code tasks:** focused configuration and helper checks, then `composer format` after PHP edits, `composer lint`, and `composer quality` as configured. The implementation Review records actual results and limitations; no implementation tests are claimed by this Spec.
