# SPEC — English baseline and browser-aware localization

**ID:** 003-globalizacao · **Status:** proposed · **Date:** 2026-10-16

**User validation for Plan:** validated. **Statement:** "aprovar". **Name:** Paulo Bezerra · **Date:** 2026-10-16.

## Problem, verified baseline, and objective

The current shell in `src/template/index.phtml` declares `pt-BR` and contains Portuguese navigation and metadata. The Vue pages in `public/assets/js/pages/` and the client in `public/assets/js/services/api.js` contain Portuguese UI and fallback errors. PHP controllers, `JsonObject`, `CsrfMiddleware`, and `HttpErrorHandler` return Portuguese messages; `AuthException` and `PostService` also carry Portuguese exception text into HTTP responses. `Blog.js` formats dates with the browser default locale. `Config` has no language settings, and neither the shell nor the API currently negotiates a language. These are code observations, not evidence that every runtime flow has been tested.

An installation must supply English UI and application messages by default, serve Portuguese automatically when the browser prefers it, and keep its HTML, Vue interface, and application-owned API feedback coherent. Maintainers must find repository-owned guidance and API reference prose in English. The existing authentication, Post, route, response-shape, and data contracts remain in force.

## Scope and constraints

- **Includes:** `en` and `pt-BR` translations for application-owned shell, Home documentation, navigation, Auth and Post flows, feedback, errors, accessibility labels, dates, title and description; configurable supported locales and fallback; English repository-owned source guidance, comments, examples, scripts, tests, README, Markdown, Dockerfile comments, and OpenAPI prose, including active and historical SDD material.
- **Outside scope:** a language picker or stored override; translation of visitor-authored Posts or other stored user data; third-party, generated, or externally owned files; delivery of a third language. A derived project may add a complete catalog and configure it without changing the language selection algorithm.
- **Constraints:** PHP 8.4, Slim 4, Vue 3 and native ES modules without a JS build; one PHP/Apache web deploy; no change to authorization, CSRF, session, URL paths, request bodies, response field names, status codes, database schema, or existing data. Do not add a package for two catalogs when existing PHP/JS capabilities suffice. Preserve meaning, decisions, names, dates, and validation evidence when translating historical material; keep quoted validation statements verbatim where translation would alter the evidence.

## Technical solution

**Technical decision:** On 2026-10-16 the user chose option A, server negotiation with a shared catalog, after comparison with browser-driven selection. The user also specified that visitors will not choose or persist a manual language.

**Chosen option A — high code impact.** A small HTTP localization component uses `Accept-Language` and validated configuration to select the locale for each request. The server renders the SPA shell with the selected `lang`, title, description, and application text, and exposes the selected locale to the Vue bootstrap through escaped, inert HTML data. PHP and Vue read the same UTF-8 JSON catalogs with stable keys and placeholders. The SPA loads its catalog before mounting and sends its selected locale as `Accept-Language` on API calls so a single loaded page keeps coherent feedback. The HTTP adapter translates application error reasons while Domain/Application remain independent of HTTP. This touches configuration, bootstrap, view, HTTP controllers/middleware/error handling, Vue pages/client, tests, browser checks, operational docs, and repository prose. It needs no migration. It adds a small catalog request and a cache-language obligation, but avoids duplicated translations and gives the first HTML response correct language metadata.

**Alternative B — high code impact, not chosen.** Vue could choose from `navigator.languages`, update the DOM language and metadata after loading, and pass that locale to the API. This has similar API and catalog work, but the first HTML response would be in the fallback language and could briefly disagree with the displayed language or accessibility metadata. It also leaves non-JavaScript HTML errors to a separate server path. Its smaller server shell change did not offset that inconsistency.

**Reason:** The Feature requires displayed and declared languages to agree throughout navigation, including the initial page. The present PHP-rendered shell makes server selection the direct way to satisfy that requirement. Security and data integrity are materially equivalent between these options because locale never grants access or changes stored data. Static catalog reads have bounded cost; configuration and cache behavior are the operational differences.

## Requirements

- **S003-01 — Validated language configuration.** Given the supplied configuration, startup accepts `en` and `pt-BR` as supported locales and `en` as fallback. A derived installation can configure an ordered supported set and a fallback within that set, provided each locale has a complete catalog. Empty, duplicate, malformed, missing-catalog, or unsupported fallback settings fail explicitly rather than silently selecting a language. Document the settings and the steps to add a catalog.
- **S003-02 — Deterministic negotiation.** Given an HTTP request without a usable `Accept-Language`, return the configured fallback. Given weighted browser preferences, select the highest-priority supported language with positive quality; honor preference order for equal quality and recognize regional variants by primary language (`pt`/`pt-*` → `pt-BR`, `en-*` → `en` in the supplied set). An explicit `q=0` excludes that language from preference matching. Unsupported preferences and wildcards resolve to the fallback when no supported language has a positive match, even if the fallback was explicitly excluded; this is the configured product fallback, not a claimed acceptable match. The selection is independent of account, session, Post data, and route.
- **S003-03 — Correct initial document and SPA language.** A page request and page fallback render escaped, localized shell text, `html lang`, title, description, navigation and accessibility text in the selected language. Vue Home documentation, Auth, Blog, Post editor, published Post, not-found view, loading/empty states, notices, and local network/CSRF errors use that same locale. Displayed dates use it too. Navigation, login, logout, and CSRF retry retain the page locale; a new page load re-evaluates browser preference. Catalog loading failure produces a visible, safe fallback instead of an empty or mixed-language application.
- **S003-04 — Localized HTTP feedback with stable contracts.** API requests negotiate their own locale; SPA requests explicitly send the page locale. All application-owned response messages used by the interface, including Auth, Post, malformed JSON, validation, unauthorized/not-found/conflict, CSRF 419, and generic 500, use the negotiated catalog. HTML error pages use it and declare their language. Preserve HTTP status, JSON field names and types (`error.status`, `error.message`, optional `error.details`, and existing success fields), route behavior, and generic non-disclosing 500 responses. Keep stable error reasons separate from translated presentation; do not use Portuguese or English exception-message string matching to choose a translation. If a catalog unexpectedly becomes unavailable, use a generic safe error in the configured fallback language without exposing internal details or mixing partial translations.
- **S003-05 — Language and cache metadata.** Localized HTML and JSON responses identify the selected application language with `Content-Language` and ensure a shared cache does not reuse one language's response for another (`Vary: Accept-Language`, preserving existing `Vary` values). The header describes application-owned text; visitor-authored fields remain verbatim. Do not use locale input as trusted HTML, a file path, an authorization signal, or persistent user state. Avoid injecting executable translation content or weakening CSP; render catalog values as escaped text and allow trusted Markdown HTML only through the existing safe renderer.
- **S003-06 — Repository and documentation language.** Translate repository-owned maintainer prose, source comments and examples, Dockerfile/config descriptions, scripts/test diagnostics, README, operational documents, OpenAPI attributes and generated reference, and active/historical `.specs/` prose to English. Preserve commands, paths, identifiers, technical meaning, historical decisions and validation records. Keep Portuguese visitor-facing text in translation catalogs. Do not rewrite third-party or generated vendor assets or user data. The on-site Home documentation remains bilingual through S003-03, while the API reference remains English maintainer material.
- **S003-07 — Regression across both locales.** With existing users and Posts, both languages preserve registration, login/logout, public reading, author-only editing, Markdown safety, CSRF handling, pagination, and unknown `/api/*` 404 JSON behavior. Existing data and Post content are not translated or migrated.

## Contracts, data, and security

Configuration names are `SUPPORTED_LOCALES` (comma-separated locale identifiers; supplied value `en,pt-BR`) and `FALLBACK_LOCALE` (supplied value `en`). Normalize configured and requested language tags for matching, but emit canonical configured tags. For this delivery, both supplied catalogs must contain matching required keys; configuration validation reports incomplete catalogs. The catalogs are UTF-8 JSON in a public static asset directory so PHP can read the same files Vue fetches without a build. Translation keys are internal identifiers, not new API fields. Interpolation escapes user-controlled values in HTML; Vue uses text bindings, never `v-html` for catalog strings. English is the authoring baseline; incomplete Portuguese catalogs fail validation instead of silently producing a mixed-language release.

The server decides from the request header and passes only a validated locale identifier to the HTML. The client loads the matching catalog before mounting and sends that exact locale in subsequent API requests, including CSRF refresh and one allowed 419 retry. It does not store locale in a cookie, session, account, local storage, or URL. Direct API consumers can use `Accept-Language` and receive the same JSON structure with localized application messages. Unknown or malformed language input falls back safely. The API's existing user/Post fields and Markdown output retain their data and escaping rules.

No schema change or migration is needed for empty or existing installations. Internal exception and validation reasons may need stable identifiers so the HTTP boundary can translate them; external status codes and shapes stay stable. Existing tests that assert Portuguese messages must be updated to assert the new English default and Portuguese negotiation, while still checking confidentiality of 500 errors. OpenAPI describes language negotiation and response metadata in English and is regenerated from code, with route parity checked.

## Acceptance and verification

- **Negotiation/configuration:** Given no header, an unsupported header, `pt-BR`, `pt-PT`, `en-US`, weighted mixed preferences, and `q=0`, when a page or API request is made, the selected locale follows S003-01/02. Unit tests cover parser and invalid configuration; HTTP integration tests cover canonical response headers and `Vary`.
- **Initial page and navigation:** Given English and Portuguese browser preferences, when `/`, `/login`, `/blog`, `/my-posts`, a Post page, or a non-API fallback is opened, the shell and mounted Vue view use the same language, including title, description, labels, empty/loading states, and dates. Browser checks cover navigation and authentication state changes in both languages and a catalog-load failure.
- **API success and failure:** Given each locale, when registration/login, invalid input, missing authentication, denied/missing Post, malformed JSON, duplicate value, expired CSRF, and an unexpected exception are exercised, application messages use the selected language with unchanged status and JSON shape; no internal exception text appears. HTTP integration tests cover these boundaries, including an unknown `/api/*` 404 and a partial network failure in the SPA.
- **Data/security:** Given an existing Post with Portuguese or English author text, when it is read or edited in either UI locale, stored title/content/slug and Markdown safety remain unchanged. Integration and browser tests cover author-only operations, CSRF retry, and XSS escaping; no migration runs.
- **Documentation:** A repository text audit finds English maintainer prose in owned active/historical files and generated OpenAPI prose, while translation catalogs retain Portuguese visitor text. Check historical decisions and validation evidence for preservation; review examples and links against actual scripts and routes.

**Applicable gate for later Code tasks:** focused tests, `composer format` after PHP edits, `composer lint`, and full `composer quality`; for SPA changes also `./tools/test-all.sh` with the active app and browser, extended to cover both locales and failure flows. Regenerate OpenAPI and run route parity checks when its source changes. These are future implementation gates, not tests claimed to have run during this Spec.
