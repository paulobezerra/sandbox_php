# SPEC — Behavioral coverage for PHP and frontend code

**ID:** 011-cobertura-testes · **Status:** proposed · **Date:** 2026-10-21

**User validation for Plan:** Paulo Bezerra approved this Spec by stating “aprovar novamente” on 2026-10-21.

## Problem, baseline, and goal

Contributors and maintainers need tests that exercise source lines and alternate outcomes, including failures and boundaries. The current PHP setup runs PHPUnit 11 and creates a Clover report, but `tools/check-coverage.php` enforces only 80% executable-line coverage. A branch-coverage checker is being added to the current PHP work, while the Vitest configuration and CI workflow do not yet collect frontend coverage or enforce thresholds.

The approved Feature requires independent backend and frontend minimums of 95% line coverage and 85% branch coverage. It recommends 100% line coverage for code authored by agents. This is a recommendation, not a CI threshold; no 100% branch-coverage target is set.

## Scope and constraints

- **Included:** Coverage expectations for authored PHP, Vue, and JavaScript production code; tests written before new behavior when practical; characterization tests for behavior-preserving refactors; independent backend and frontend line and branch reports and thresholds.
- **Out of scope:** Application behavior or HTTP contract changes; treating line coverage alone as evidence of behavior completeness; any 100% branch requirement; measuring tests, third-party dependencies, or generated build artifacts as application coverage.
- **Constraints:** Keep PHP 8.4, Slim 4, PHPUnit 11, Vue 3, Vitest 5, Vite, npm, GitHub Actions, and the existing PHP/Apache deployment. Prefer established, maintained market tools for tests, CI, and CD. Coverage tooling is development/CI-only. Do not change production application code solely to increase a metric. Backend and frontend test jobs run with PHPUnit and Vitest respectively, without starting the full application or depending on a database or external API. Playwright/browser end-to-end testing is not required for this feature and may be reconsidered in future work. No database schema or API changes.

## Technical solution

**Technical decision:** Enforce line and branch coverage independently for each stack. Set the CI minimums to 95% line and 85% branch coverage for both PHP and frontend source. The user explicitly approved the revised Feature on 2026-10-21 (“aprove”). The user's earlier decision to use PHP branch coverage rather than path coverage remains applicable: a report for a unit-tested entity enumerated more than 4,000 paths with only 2 covered, making path percentage an impractical gate for this project.

**Selected solution — native coverage metrics from existing test runners (moderate impact).** For PHP, collect line and branch data with PHPUnit and Xdebug, report Clover metrics, and enforce separate thresholds: 95% executable lines and 85% branch outcomes. For frontend, enable Vitest coverage on all authored `frontend/src/**/*.{js,vue}` files and enforce 95% lines and 85% branches. Use a Vitest-compatible coverage provider as a development dependency, pinned compatibly with the current Vitest release. CI reports each stack and metric separately and fails when any threshold is missed. PHP coverage tests added for this feature are unit tests only. This solution reuses the existing PHP and frontend test runners and does not require application refactoring.

The tradeoff is additional CI time and memory for Xdebug, plus a frontend coverage provider dependency. The frontend dependency must remain development-only and must not enter the production build. Coverage percentages remain execution metrics; unit and frontend tests must also assert observable results and failure behavior. Keep the two test jobs self-contained and fast by using only repository code and controlled test doubles at external boundaries.

**Alternative considered — retain line-only coverage (low impact, rejected).** The existing PHP line checker could remain with a corrected 95% threshold, but it would not verify the Feature's 85% branch minimum, and the frontend would still have no enforced coverage. This does not satisfy the approved Feature.

**Reason for the decision:** The Feature explicitly defines the percentages and applies them independently to both layers. PHPUnit/Xdebug supplies PHP line and branch metrics; Vitest's coverage provider supplies frontend line and branch metrics. A test runner per layer keeps reporting and failure local to the affected CI job. PHPUnit path coverage is excluded from the gate based on the user's recorded decision and the observed path-count explosion.

**Tooling preference:** Prefer established, maintained tools already adopted by the project or widely used in the relevant ecosystem: PHPUnit for PHP tests, Vitest for frontend tests, and GitHub Actions for CI/CD. When selecting coverage reporting and threshold enforcement, first check capabilities in those tools and their supported extensions. Add a dependency, a second runner/platform, or custom project-specific tooling only when the established stack cannot satisfy a requirement; Plan must record the gap, compatibility/support evidence, and reason for that choice. Small project-specific glue is acceptable when needed to connect supported reports or enforce a requirement that market tools do not provide directly.

The testing guidance uses “unit” for behavior isolated at any layer of this system, with dependencies outside the unit replaced by test doubles; “integration” for interactions among this repository's own components, with databases and external APIs replaced by controlled doubles; and “characterization” for the purpose of recording existing behavior before a behavior-preserving refactor. Characterization is not a third test level: a characterization test may be unit or integration scope depending on which boundary it records. It must use the same test and assertions on the base (`main` or historical `master`) and feature branches and pass on both, including after the feature refactor. This follows the [ISTQB integration-testing definition](https://glossary.istqb.org/en_US/term/integration-testing?exact_matches_first=true&term=verification), PHPUnit's guidance on isolating a unit with test doubles, and Michael Feathers' treatment of characterization tests in *Working Effectively with Legacy Code*.

## Requirements

- **S011-01 — PHP line coverage:** Given the PHP test suite and authored executable PHP sources, CI reports aggregate line coverage using PHPUnit/Xdebug and Clover statement metrics. It passes at 95% or above and fails below 95%. Include application code and executable repository PHP tooling/configuration/migrations; exclude `tests/`, installed dependencies, and generated files. Missing, malformed, or empty coverage data must fail rather than pass. Affected consumers: maintainers, contributors, and CI.
- **S011-02 — PHP branch coverage:** Given the PHP test suite and authored executable PHP sources, CI reports aggregate branch coverage from Xdebug branch data and fails below 85%. Missing branch data, a missing driver, an invalid report, or an empty branch denominator must fail with a diagnostic. A line-only report cannot satisfy this requirement. Tests added to improve coverage do not change production application code solely to improve the score. Affected consumers: maintainers, contributors, and CI.
- **S011-03 — Frontend line and branch coverage:** Given the Vitest suite, CI reports line and branch coverage separately for every authored Vue/JavaScript file under `frontend/src/`, including files not imported by existing tests. It passes at 95% line coverage and 85% branch coverage, and fails when either metric is below its threshold. Missing, malformed, or empty data for either metric fails the job. Exclude tests, dependencies, generated bundles, and third-party assets. Affected consumers: frontend contributors, maintainers, and CI.
- **S011-04 — Test selection and practice:** When adding behavior, contributors ordinarily write a failing test for the expected result before implementation when practical, then make it pass. Plan tasks identify test purpose, level, affected boundary, and why that level proves the acceptance criteria. A unit test can target any layer of this application; execute the target code and replace dependencies outside that unit with mocks, stubs, or fakes. Use integration tests to verify interactions across this repository's own components; keep the test focused on project code and replace databases, external APIs, and other outside services with controlled doubles. Run backend and frontend tests through PHPUnit and Vitest respectively without starting the full application or external services. Before behavior-preserving refactors with uncertain or incomplete contracts, add characterization tests that record current externally observable results. Use the same characterization test and assertions against the base (`main`, or historical `master`) and feature branches; it must pass on both before and after the refactor. Characterization is a test purpose, not a level, and may be unit or integration scope. If captured behavior conflicts with the requested behavior, record the discrepancy and resolve scope before changing it. Code follows the Plan's selection and adds another test level only when it proves a distinct risk the selected level cannot establish. If test-first work is impractical, explain why and still verify the resulting contract. Cover relevant success, invalid input, denied access, failure, and state-preservation outcomes. Contributors and agents should aim for 100% line coverage on authored code; there is no 100% branch target. Playwright/browser end-to-end coverage is deferred and is not required by this Feature.
- **S011-05 — Independent CI enforcement:** On pull requests and qualifying pushes, backend and frontend jobs each report their line and branch percentages. Each layer fails independently if line coverage is below 95% or branch coverage is below 85%, and a failure prevents the workflow's quality/release dependencies from passing. Reports name the metric and numerator/denominator so line coverage cannot substitute for branch coverage. Affected consumers: `.github/workflows/quality-and-release.yml` and repository maintainers.
- **S011-06 — Market tooling preference:** Plan and Code prefer established, maintained tools for tests, CI, and CD, using the project's existing PHPUnit, Vitest, and GitHub Actions stack where it meets the requirement. Before adding a second runner/platform, dependency, or custom coverage tool, verify whether the current tool or a supported market extension can meet the acceptance criteria. If custom glue or another tool is necessary, Plan records the unmet capability, compatibility/support evidence, and rationale; Code implements only that justified gap. Affected consumers: feature contributors, maintainers, test suites, and CI/CD workflows.

## Contracts, data, and security

This Spec changes development and CI checks only. It adds no HTTP routes, request/response fields, authorization behavior, persisted data, migrations, or runtime application dependency. Coverage tooling must not be shipped as production assets. CI reports and fixtures must not contain secrets or real application data.

Coverage scope is authored executable PHP outside `tests/` and installed dependencies, including `src/`, `public/index.php`, `tools/`, Phinx configuration, migrations, and repository PHP configuration. Frontend scope is authored JavaScript and Vue under `frontend/src/`. Third-party files, tests, generated Vite output, and committed vendor assets are excluded. Any additional exclusion within these source scopes must be explicit, narrowly justified, and visible in configuration; it must not conceal testable behavior.

## Acceptance and verification criteria

- **PHP line success/failure:** Given Xdebug coverage mode and the PHPUnit suite, when CI generates and checks the report, then it prints the aggregate line percentage and passes at 95% or above; a lower score fails. Test: coverage-gate cases at, above, and below 95%, plus confirmation that uncovered authored PHP files remain in the denominator.
- **PHP branch success/failure:** Given the same suite with Xdebug branch collection enabled, when CI checks the report, then it prints branch counts and passes at 85% or above; a lower score, absent branch fields, malformed report, missing driver, or zero branches fails. Test: gate cases at, above, and below 85%, and invalid/missing/empty branch reports.
- **Frontend success/failure:** Given Vitest and the configured coverage provider, when CI collects coverage, then all authored `frontend/src` JS/Vue files appear in the report and the job passes only when line coverage is at least 95% and branch coverage at least 85%. Test: inspect coverage for both imported and unimported source files, exercise threshold pass/fail cases for each metric, and verify absent or empty data fails.
- **Behavior and test-level selection:** Given a rule in any application layer, Plan specifies an isolated unit test with outside dependencies doubled. Given behavior that depends on interactions among project components, Plan specifies an integration test using controlled doubles for databases and external APIs; the test runs under PHPUnit or Vitest without starting the full application. Given a behavior-preserving refactor with uncertain behavior, Plan specifies a characterization test whose unchanged test and assertions pass against both the base and feature branches after the refactor. Characterization may be unit or integration scope. For new behavior, tests assert expected results and relevant failure/boundary outcomes, are written first when practical, and explain exceptions. Test: review Plan rationale and focused test runs on the appropriate branches.
- **Integration/compatibility:** Given a pull request or qualifying push, when backend and frontend jobs run, then they report their four thresholds independently and any failed threshold fails CI. PHPUnit and Vitest run without the full application, a database, or external APIs; the coverage provider is development-only. Playwright/browser end-to-end tests are not part of this Feature's CI gate and may be considered in future work. Test: run CI-equivalent PHP and frontend coverage commands, the complete PHPUnit/Vitest suites, and the frontend production build during Review, with no app/database/API service startup.
- **Tool selection:** Given a Plan task requiring test execution, coverage, CI, or CD, when a tool is selected, then the task prefers a maintained tool already used by the project or a supported extension of it. A new runner/platform, dependency, or custom utility is proposed only when existing market tools cannot meet a stated requirement, with compatibility/support evidence and a recorded rationale. Test: review Plan decisions and Code dependencies/workflow changes against that rationale.

**Applicable gate:** During implementation, run focused unit/Vitest checks for changed behavior and the applicable coverage gates. At the first Review, run the complete PHP and frontend suites, all four coverage thresholds, `composer lint`, and `npm --prefix frontend run build`. Inspect CI wiring to ensure Xdebug is available only where needed and the frontend provider does not ship in production assets. No implementation checks were run during this Spec update.
