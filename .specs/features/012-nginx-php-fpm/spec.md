# SPEC — Secure local PHP runtime with Nginx and PHP-FPM

**ID:** 012-nginx-php-fpm · **Status:** proposed · **Date:** 2026-10-25

**User validation for Plan:** Paulo Bezerra approved this Spec by stating “aprovar” on 2026-10-25.

## Problem, baseline, and goal

The local Docker environment currently runs the application in one Apache/PHP container. `Dockerfile` uses the moving `php:8.4-apache` tag and `compose.yaml` publishes that container on host port 8080. The actual PHP patch in an existing image has not been verified. The `mysql` service uses the named `mysql_data` volume. Production remains Apache shared hosting through the documented release workflow.

The goal is to make both documented Docker paths use Nginx for HTTP and a security-fixed PHP 8.4-FPM runtime, while keeping the existing application, local URL, MySQL data, and Apache shared-hosting deployment available. The production Compose path is a reusable starting point for adopters hosting the skeleton on infrastructure they control, such as a VPS; it is not a claim that this repository's production environment runs Docker or that the template has been fully validated on a VPS. Because README, the Home page, and project guidance tell adopters to use `compose.prod.yaml`, the configuration should be corrected where repository evidence permits and the documentation must clearly state the validation limit and adopter responsibility.

## Scope and constraints

- **Included:** Local development and documented Docker production images/Compose topologies; Nginx configuration; fixed and verifiable PHP 8.4 runtime; local configuration/build checks; documentation of the production example's validation limits.
- **Out of scope:** Changing the actual automated Apache shared-hosting deployment, installer, or release workflow; application behavior; database engine/schema; and existing data.
- **Hard constraints:** PHP 8.4 must include the fixes for CVE-2026-109618 and CVE-2026-109619 (PHP 8.4.27 or vendor build confirmed to contain both); FPM is not published on a host port; local application remains on `http://localhost:8080`; preserve MySQL and `mysql_data`; retain the Apache shared-hosting path.
- **Decision drivers:** Prevent rebuilds from silently selecting a vulnerable PHP patch, preserve the local developer workflow, keep the FPM boundary private, minimize complexity, and avoid implying this repository deploys production with Docker.

## Decision brief

**Verified baseline:** `Dockerfile` starts from `php:8.4-apache`, enables Apache rewrite, installs the existing PHP extensions, and starts Apache in the development Compose command. `compose.yaml` publishes `8080:80`, bind-mounts the repository, and defines MySQL with `mysql_data`. `compose.prod.yaml` and the production/release documentation describe a separate deployment path; this Feature explicitly excludes changes to it. Apache shared hosting is documented in `README.md` and automated by `.github/workflows/quality-and-release.yml` and `tools/deploy-shared-hosting.sh`. No local Nginx/FPM configuration exists.

**Feature decision drivers:** The security-fixed PHP requirement applies to both Docker paths. Maintaining the local URL, MySQL data, application contracts, and Apache shared-hosting deployment are hard constraints. Low operational complexity and reusable Docker guidance are priorities. Feature security references identify PHP 8.4.27 as fixed for both CVEs.

### Single viable solution

Use distinct Nginx and PHP 8.4-FPM services in both Docker Compose paths. Pin the PHP image to a security-fixed patch (PHP 8.4.27 or later explicitly verified vendor-patched build), and make the selected patch visible and verifiable during build/runtime checks so an implicit moving tag cannot bypass the requirement. Keep the existing development bind mount, Composer setup, extensions and Xdebug behavior. Nginx serves `public/`, sends application routes through `public/index.php`, denies direct execution of other PHP files, and forwards FastCGI to `app:9000`. In production, keep optimized dependencies/assets, production PHP settings, and only expose Nginx; both services must use matching application files/assets. Preserve each Compose path's MySQL service and named volume configuration. Update README and Home copy to distinguish optional Docker production from the active shared-hosting release path. Leave Apache shared hosting and its release workflow unchanged.

- **Affected components:** `Dockerfile`, `compose.yaml`, `compose.prod.yaml`, Nginx configuration, Docker production image assembly, README and localized Home copy, and Docker configuration/runtime checks.
- **Estimated code impact:** moderate.
- **Benefits:** Meets the required local architecture and CVE patch constraint, keeps FPM private, retains the familiar local URL and persistent database, and preserves the provider-dependent Apache deployment.
- **Costs and risks:** Adds Nginx/FPM configuration to both Docker paths; two containers must use consistent application paths and matching production public assets. Local configuration/build checks cannot establish compatibility with every VPS, reverse proxy, firewall, DNS, TLS, storage, or backup setup. Documentation must disclose this limit and leave environment-specific review and operation to the adopter. A future PHP security update must deliberately update the fixed image version and its verification evidence.
- **Why relevant alternatives fail:** Keeping Apache in Docker does not satisfy the requested Nginx/FPM architecture. A combined Nginx/FPM container requires custom multi-process supervision and adds complexity without a Feature benefit. Deleting `compose.prod.yaml` would contradict README, Home, and project guidance that explicitly instruct adopters to use it. Presenting it as fully validated would overstate the available evidence; the correct treatment is a maintained reusable example with an explicit validation caveat. Removing Apache shared hosting would exceed the requested change and disrupt the active release path.
- **Evidence:** `Dockerfile`, `compose.yaml`, `compose.prod.yaml`, `docker/apache/000-default.conf`, `README.md`, `public/assets/i18n/en.json`, `public/assets/i18n/pt-BR.json`, `frontend/src/spa/pages/Home.vue`, `AGENTS.md`, `.github/workflows/quality-and-release.yml`, `tools/deploy-shared-hosting.sh`; PHP advisory and release links recorded in `feature.md`.

**Recommendation:** Proceed with Nginx/PHP-FPM in both documented Docker paths and keep `compose.prod.yaml` as a reusable VPS-oriented example. Correct configuration and documentation using repository-local evidence. Run only checks that establish local properties, such as Compose configuration resolution and image builds when the environment permits; do not imply these prove VPS deployment. State in the documentation that the production example has not been fully validated in a real target environment and that the adopter must review and validate it for their VPS, proxy/TLS, secrets, firewall, persistence, and backup setup. The user's explicit rule makes maintaining the referenced production example part of this request. The deviation from the Feature's original Docker production exclusion is limited to correcting this existing example and its guidance; the automated shared-hosting deployment remains unchanged. Do not publish or infer the repository's actual production host, filesystem/deployment path, or access details.

**Decision requested:** None — proceed with the user's explicit direction to retain and correct the documented Compose production path. This direction approves the scope deviation stated above; it is not Spec validation for Plan.

## Technical solution

**Technical decision:** On 2026-10-25, use separate Nginx and PHP-FPM services in development and retain/correct the documented Docker production Compose path as an adopter template. The user directed that a Compose file referenced in documentation should be corrected and retained, and clarified that it is for adopters who may host the skeleton on a VPS. Local checks may verify configuration and image construction but cannot validate a real adopter's infrastructure. Documentation must say the example is not fully validated in a target VPS and that the adopter is responsible for environment-specific validation. Do not disclose the repository's actual production host, deployment path, or credentials.

The development `app` service uses PHP-FPM on the internal Compose network, retaining required PHP extensions, Composer startup behavior, Xdebug, and the repository bind mount. The production `app` image uses production PHP settings and optimized Composer dependencies; the production `nginx` image contains the matching `public/` tree and built frontend assets. Nginx is the only service publishing HTTP in each Compose path and forwards FastCGI to `app:9000`; FPM has no host-published port. Nginx serves existing public files directly, routes application paths to the front controller, and denies other PHP entry points. The selected PHP image version must be explicit and confirmed fixed for both listed CVEs; do not rely on an unbounded `8.4` tag. Preserve MySQL service/volume definitions in both paths. Update README and both Home locales to distinguish optional VPS/adopter Docker deployment from the active shared-hosting release path, and state that the Docker production example has not been fully validated on a real target VPS. Do not include the actual production host, actual deployment path, account details, credentials, or secrets in project documentation. Do not change Apache shared-hosting files or release workflow.

**Reason for the decision:** Separate services use standard container boundaries and avoid custom process supervision. A pinned patch plus explicit verification prevents an unnoticed return to a vulnerable moving tag. The existing production Compose path is explicitly recommended by project documentation, so deleting it or leaving it untested would mislead adopters. Its maintenance does not replace or modify the actual shared-hosting release path.

## Requirements

- **S012-01** — Given the local development Compose configuration, when the stack starts, the application remains available at `http://localhost:8080`, with HTTP handled by Nginx and PHP requests executed by PHP-FPM. Existing static assets are served directly and non-file application paths reach `public/index.php`. Consumers: developers, browser, API.
- **S012-02** — Given a compatible VPS and adopter-provided production environment values, when the adopter configures and starts `compose.prod.yaml`, Nginx serves the application and compiled assets on `${APP_PORT:-8080}` and forwards PHP execution to the matching production PHP-FPM image. Consumers: adopters, operators, browser, API. This target-environment behavior is not fully validated by this project.
- **S012-03** — When either Docker runtime image is built or started, its PHP 8.4 patch is explicit and verifiably includes fixes for CVE-2026-109618 and CVE-2026-109619; an unresolved or vulnerable patch selection must fail the applicable build/configuration check rather than silently proceed. Consumers: developers, maintainers, operations.
- **S012-04** — In both Compose paths, PHP-FPM listens only on the internal Compose network and has no published host port. Direct HTTP access to PHP files other than `public/index.php` is denied; normal page/API fallbacks continue to follow the application's existing contract. Consumers: developers, adopters, security, API.
- **S012-05** — Rebuilding/recreating application runtime containers preserves each Compose path's existing MySQL service configuration and named `mysql_data` volume; this change does not run migrations, reset data, or alter schema. Consumers: developers, adopters, application persistence.
- **S012-06** — Apache shared-hosting configuration, installation/release path, and automated workflow remain usable and unchanged. Documentation distinguishes active shared-hosting releases from optional Docker production instructions and gives accurate commands/configuration for both. Consumers: shared-hosting operators, downstream adopters.

## Contracts, data, and security

- Preserve the local URL `http://localhost:8080` and documented production mapping `${APP_PORT:-8080}:80`. Nginx owns host HTTP in both Compose paths; PHP-FPM is reachable only as `app:9000` inside Compose.
- Use `public/` as Nginx document root. Serve existing files directly; route missing application paths to `index.php` with query strings preserved. Only the front controller is passed to FastCGI; deny other `.php` paths.
- Select an explicit PHP 8.4 patch whose fix status for both CVEs is supported by the PHP project advisory/release or vendor evidence. No floating major/minor-only tag may satisfy this contract without an independently enforced fixed-version check.
- Preserve MySQL 8.4 service and named-volume configurations in both Compose paths. Do not connect to or modify a real production database during local verification; do not perform migration, rollback, reset, or volume removal against existing data.
- Do not change application routes, payloads, authentication/session/CSRF behavior, Apache shared-hosting behavior, or release workflow.

## Acceptance and verification criteria

- **Local runtime:** Given the development Compose configuration, when required services are built and started, `http://localhost:8080` serves the app, a static asset, and a representative application/API path through FPM. Verify Compose configuration/build and focused HTTP integration using local Docker services.
- **Documented Docker production path:** Check Compose configuration and build the production images when local Docker is available. These checks only prove local parsing/build properties; do not claim they prove deployment on a VPS. The documentation must state that the example has not been fully validated in a real target environment and the adopter must validate it against their infrastructure before relying on it.
- **Runtime security:** Given the selected image, when its PHP version and advisory evidence are inspected, the exact 8.4 patch is fixed for both CVEs; a deliberately unverified/vulnerable version cannot pass the version guard. Verify image/runtime version and the configuration/build guard.
- **Network and routing boundary:** FPM has no published host port; direct request to a non-front-controller PHP file is denied, while an unknown `/api/*` path reaches the application and returns its existing JSON 404. Verify with Nginx HTTP requests and the resolved Compose port configuration.
- **Persistence and scope:** MySQL service and named volume configuration remain present in both Compose files. No production database or real deployment environment is used for verification. Confirm Apache shared-hosting configuration, installer, and release workflow remain unchanged.
- **Documentation:** README and Home copy accurately describe both Docker paths and their separation from the automated Apache shared-hosting release. State that Docker production is an adopter template not fully validated on a real VPS and that adopters own environment-specific validation. Include no actual host, deployment path, account/access details, credentials, or secrets.

**Applicable gate:** Run focused local dev/prod Compose configuration checks and image builds when available because both Docker topologies, FastCGI routing, PHP patch selection, and static-file handling change. These checks do not establish VPS deployment compatibility; a simulated environment or broad automated suite would not prove compatibility with arbitrary adopter infrastructure. Make the validation limitation explicit in user-facing production guidance and leave target-environment validation to the adopter. Do not connect to, change, or disclose details of any real production environment. Verify the MySQL volume configuration without resetting or migrating data. Run application tests only if application behavior/code changes. The shared-hosting deployment remains out of implementation scope.
