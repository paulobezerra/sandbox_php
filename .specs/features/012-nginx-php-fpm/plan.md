# PLAN — Secure local PHP runtime with Nginx and PHP-FPM

**Feature:** [feature.md](feature.md) · **Spec:** [spec.md](spec.md) · **Date:** 2026-10-25 · **Status:** open

**User validation to start Code:** Paulo Bezerra approved this Plan by stating “aprovar” on 2026-10-25.

## Delivery strategy

Deliver the local runtime first, preserving the documented local URL and existing MySQL volume. Then adapt the documented Docker production example for adopters, sharing the same PHP patch policy, private FPM boundary, Nginx routing, and application assets. Keep the Apache shared-hosting deployment and release workflow unchanged. Production Compose parsing and image builds are local template checks only; they do not validate a real VPS, which remains the adopter's responsibility. No database migration, reset, or volume cleanup is part of this work.

## Tasks

- **T012-01 — Run the local development stack through Nginx and private PHP-FPM.** **Requirements:** S012-01, S012-03, S012-04, S012-05. **Precondition:** The existing development Compose configuration and `mysql_data` volume are the baseline; preserve current data and do not run migrations. **Scope:** Change the development PHP image to an explicit PHP 8.4 FPM patch whose fixes for both CVEs are supported by PHP project or vendor evidence; add a build/runtime guard that rejects an unresolved or vulnerable selection. Preserve required PHP extensions, Composer startup/install and asset publishing, Xdebug, and the repository bind mount. Add an Nginx service/configuration that serves `public/`, routes missing application paths to `public/index.php` with query strings preserved, serves existing static assets, denies direct access to other PHP files, and forwards FastCGI to `app:9000`. Publish only Nginx at host port 8080. Keep the MySQL service and `mysql_data` volume unchanged. **Acceptance:** Compose resolves with Nginx owning `8080` and no host port for FPM; the selected runtime reports the pinned fixed PHP 8.4 patch. Once built and started, `http://localhost:8080` serves the application and an existing static asset, a representative application path and unknown `/api/*` path reach the application with its existing response contract, and direct access to a non-front-controller PHP file is denied. The MySQL service/volume identity remains intact and a read-only application/database check succeeds without data reset or migration. **TDD/characterization:** Before implementation, run focused topology/config assertions that fail on the current Apache-only baseline and cover the services, port ownership, FPM target, document root/front-controller routing, PHP denial, PHP patch guard, and MySQL volume. Then build/start only the required local services and exercise the HTTP cases and read-only persistence check. **Gate:** `docker compose config`, development image build, runtime PHP version/advisory evidence check, and focused HTTP checks; inspect resolved port and volume configuration. Do not run database migrations, rollback, reset, or remove volumes. Application tests are needed only if application behavior changes. **Dependencies:** none.

- **T012-02 — Maintain the Docker production example for adopter deployments.** **Requirements:** S012-02, S012-03, S012-04, S012-05, S012-06. **Precondition:** T012-01 establishes the shared PHP-FPM/Nginx configuration and fixed-version policy; its code and checks must be complete before this task. **Scope:** Adapt the production image assembly and `compose.prod.yaml` to separate PHP-FPM and Nginx services using the same explicitly fixed PHP 8.4 patch and guard. Ensure Nginx contains the matching public application files and compiled frontend assets, publishes only `${APP_PORT:-8080}:80`, and uses the same safe front-controller, static-file, and non-front-controller PHP rules. Preserve production PHP settings and optimized Composer dependencies. Preserve the production MySQL service and named volume. Update README and English/Brazilian Portuguese Home guidance to distinguish optional adopter-operated Docker hosting from the active Apache shared-hosting release path, document accurate commands, and state clearly that local config/build checks do not fully validate a VPS and adopters must validate their own proxy/TLS, secrets, network, persistence, and backup setup. Do not expose real host or access details. **Acceptance:** Production Compose resolves with only Nginx publishing HTTP, FPM private, matching app assets, explicit fixed PHP patch, and unchanged MySQL volume; production images build when Docker is available. Documentation describes this as an adopter template with the stated validation limit and accurately preserves the active shared-hosting path. Apache configuration, installer, and release workflow have no changes and remain usable. No real production host/database is contacted. **TDD/characterization:** Before modifying the production topology, run focused Compose assertions against current production configuration that fail for the missing Nginx/FPM split, and check that MySQL/volume identity is preserved. Build both production images and inspect the PHP version when local Docker permits; validate documentation statements and inspect the final diff for unchanged shared-hosting files/workflow. **Gate:** `docker compose -f compose.prod.yaml config` with non-secret placeholder values, production image build, fixed-version evidence/guard check, resolved port and volume inspection, and targeted documentation/diff review. These checks prove local configuration/build properties only, not VPS deployment. **Dependencies:** T012-01.

## Risks and final verification

The two production services must contain matching application versions and built assets; verify their Docker build contexts and paths. PHP patch security must be substantiated by the PHP advisory/release or vendor evidence, not inferred from the image tag alone; a later security update will require an intentional version/evidence update. Docker availability may limit build and HTTP checks; record any such limitation and leave the affected evidence pending. Confirm throughout that no database operation alters existing data and that the Apache shared-hosting deployment and release workflow remain untouched.
