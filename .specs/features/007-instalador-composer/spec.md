# SPEC — Start a reusable project from Composer

**ID:** 007-instalador-composer · **Status:** proposed · **Date:** 2026-10-18

**User validation for Plan:** validated. **Statement:** "aprovar". **Name:** Paulo Bezerra · **Date:** 2026-10-18. The technical decisions below are not validation.

## Problem, baseline, and goal

The current repository is a public PHP application skeleton. Its `composer.json` declares `app/slim-vue` as a project, but that name does not identify the maintained repository as an installable project package. The README currently directs developers to `git clone`, which brings the skeleton's Git history into the destination. The repository has a root `.gitignore` for local environment, IDE, and generated dependency files. SDD Lite is independently maintained and used as a globally installed skill; this repository's README already points to that standalone workflow.

The goal is to provide a Composer `create-project` path that installs the maintained application files into a chosen destination, discards the skeleton's VCS metadata, and guides the developer to initialize a fresh Git repository and complete first-use setup. The generated project documentation will recommend SDD Lite as an optional, separately installed tool.

## Scope and constraints

- **Included:** Composer project metadata and distribution configuration; a documented `composer create-project` command with a caller-selected destination; fresh-repository and first-use instructions; ignore rules suitable for a derived project; optional SDD Lite installation guidance; expanded README and Home documentation that explain the delivered skeleton, Docker Compose setup, explicit migrations, production and shared-hosting deployment, and technology references; bilingual technology logos/links on Home; removal of links to skeleton-only `.specs` artifacts from generated documentation.
- **Out of scope:** changing Auth/Posts behavior or architecture; database creation, migration, or deployment automation; a custom generator framework; installing SDD Lite as a Composer dependency; copying SDD Lite implementation files into generated projects; automatic synchronization with upstream; registering or publishing the package to a remote registry as part of this change.
- **Constraints:** retain PHP 8.4, Slim 4, Vue 3 native ES modules, and no JavaScript build step. Do not include `.env`, dependency directories, or upstream Git history in the generated project. Do not add dependencies or change application APIs or schema.

## Technical solution

**Technical decision:** use Composer's native `create-project` for a project package named `paulobezerra/sandbox-php`, with the destination passed as the second argument. Require an empty or nonexistent destination; Composer creates a missing destination and rejects a populated one. Use `--remove-vcs` in the documented command to explicitly remove the upstream VCS metadata. The setup instructions then run `git init` in the generated directory so its owner begins a new repository and history. The package must be made available from Packagist before the concise command is usable by the public; external registration/publication is a release prerequisite, not part of this implementation step.

The generated project does not contain SDD Lite source files or this repository's `.specs` history/context. The README will point to the canonical [paulobezerra/sdd-lite repository](https://github.com/paulobezerra/sdd-lite) and recommend installing it separately when desired; users who opt in follow that project's current installation instructions and initialize their own project context. This avoids a stale embedded copy and avoids shipping skeleton-specific decisions as the derived project's own context.

The README is the full setup and operations guide. It will cover Composer project creation, requirements and environment configuration, starting Docker Compose, applying and checking migrations explicitly, opening the app, useful service commands, production Compose, and the existing shared-hosting deployment procedure. It will describe what the skeleton includes and its material limitations, and link to official documentation for the principal runtime, framework, frontend, database, container, migration, and API/documentation tools. The Home page will provide the same orientation in concise English and Brazilian Portuguese: a Composer/Docker quick start, explicit migration step, included capabilities and limitations, shared-hosting and customization links, and a technology section with official reference links. It will point to the README for complete operating and deployment instructions.

For marketing clarity, Home will show local SVG marks for the main technologies as linked, labeled visual badges. Each mark has adjacent visible text and an accessible name; SVGs are served locally so the page adds no external icon CDN or JavaScript dependency. The exact set should remain limited to the technologies prominently described on Home, while the README can list supporting libraries as text links.

**Reason for the decision:** Composer officially supports creating a project from a named package into a selected directory, and provides `--remove-vcs` to force removal of the source VCS metadata. This uses the existing package manager and repository distribution rather than adding a generator or build tool. A clean Git history still requires an explicit `git init` after project creation; documenting that step is simpler and more portable than adding a custom post-install framework. The stable Packagist package identity is a release prerequisite because Composer checks Packagist by default. The separately maintained SDD Lite skill remains authoritative and can be installed or updated independently. Detailed README instructions reduce setup guesswork, while a concise bilingual Home gives visitors a useful overview without replacing the README. Local, accessible SVG marks provide the requested technology visuals without runtime network dependencies.

**Feature deviation, explicitly validated:** Feature 007 says generated projects receive the “SDD Lite workflow” and “SDD Lite materials.” On 2026-10-18, Paulo Bezerra confirmed that a Feature does not always contain the most technically appropriate solution and approved replacing that delivery with optional SDD Lite guidance in the README. Impact: generated projects do not inherit the SDD Lite implementation or this skeleton's `.specs` artifacts; developers who want the workflow install the standalone skill and initialize their own project context. `feature.md` remains unchanged as the original product record.

**Alternatives:** embedding a copy of SDD Lite would make generated projects self-contained but create a second copy that can drift from the independently maintained workflow. Requiring SDD Lite as a Composer dependency would couple an agent workflow to PHP application dependency installation and still need an update model. Both have higher maintenance and operational cost than a documentation link to the canonical standalone project. A bespoke generator would duplicate Composer's project creation behavior and add unnecessary code.

## Requirements

- **S007-01 — Create from Composer:** given a supported PHP/Composer environment and an empty or nonexistent destination, when the developer runs the documented `composer create-project` command, then Composer installs the application into that destination and dependencies resolve from the package lock/constraints. Consumers: developers, Composer, application files.
- **S007-02 — Protect populated destinations:** given a destination containing files, when the developer runs the documented command, then project creation fails without overwriting or merging the existing contents. Consumers: developer files and Composer setup.
- **S007-03 — Start with independent Git history:** given a successful project creation, when the developer follows the documented `git init` step, then the destination has a new Git repository with no upstream remote or inherited commits. Consumers: Git and project owner.
- **S007-04 — Keep generated projects clean:** given a project created from the distributed package, then it contains no upstream `.git` metadata, `.env`, `vendor/`, or skeleton `.specs/` context/history; its `.gitignore` excludes local secrets and generated/dependency files. Consumers: package archive, Composer, Git, project owner.
- **S007-05 — Keep SDD Lite optional and current:** given a developer who wants SDD Lite, when they follow the README reference, then they reach [the canonical standalone repository](https://github.com/paulobezerra/sdd-lite) and its current installation instructions; a developer who does not want it can complete application setup without installing it. The distributed README does not link to excluded skeleton-only `.specs` artifacts. Consumers: README and SDD Lite maintainers.
- **S007-06 — Explain first use and development:** given a newly created project, when the owner follows the README, then Composer creation, prerequisites, environment setup, fresh Git initialization, Docker Compose startup, explicit migration/status commands, app URL, and basic operational commands are clear; the steps do not deploy or create a database automatically. Consumers: README and application operator.
- **S007-07 — Explain deployment choices:** given an operator preparing a deployment, when they read the README, then Docker production and shared-hosting deployment are explained as separate paths, including environment/security requirements, database backup and migration expectations, the shared-hosting deploy script's prerequisites and behavior, and links to relevant project documentation. Home summarizes the distinction and links to the full guidance. Consumers: README, Home, and application operators.
- **S007-08 — Describe what the skeleton provides:** given a developer evaluating the generated project, when they read the README or Home, then they can identify the included Auth/Posts behavior, API, architecture, frontend delivery model, major dependencies, and important demo limitations. Consumers: README and Home visitors.
- **S007-09 — Link technology references:** given a developer who wants to learn or verify a technology, when they read the stack documentation, then principal technologies and supporting libraries link to their official project or documentation pages. Consumers: README and Home visitors.
- **S007-10 — Present accessible technology marks:** given a visitor viewing Home in either supported locale, then the prominently described technologies have locally served SVG marks with visible text labels and accessible names, and the page does not rely on an external icon CDN. Consumers: Home page, locale catalogs, and static assets.

## Contracts, data, and security

No HTTP, authentication, authorization, session, database, migration, or application data contract changes. The package continues to require PHP `^8.4` and the existing application dependencies. The generated project must exclude the real `.env`, upstream `.git` history, `vendor/`, generated Swagger UI assets, and skeleton-specific `.specs` files. The example `.env.example` remains available for setup. Composer must reject a populated target instead of overwriting or merging its files. The package metadata and README must not introduce an automatic database migration or deployment action.

The package should use Composer's archive exclusion mechanism (including VCS archive metadata where needed) to prevent `.specs/` from being included in the generated distribution while retaining the files in this repository. Confirm behavior for the exact package distribution source during implementation; if the chosen dist source does not honor the configured exclusion, adjust package distribution metadata and test the resulting archive.

## Acceptance and verification criteria

- **Success:** given a temporary empty or nonexistent destination, when `composer create-project` uses the local/test package source, then the application files install, Composer completes dependency installation, and the documented initialization creates a new repository without the upstream history. Test: Composer integration scenario against a local VCS/package fixture and inspect `git log`, remotes, and expected files.
- **Failure/boundary:** given a temporary destination with a sentinel file, when creation is attempted, then Composer exits unsuccessfully and the sentinel remains byte-for-byte unchanged. Test: Composer integration scenario in a temporary directory.
- **Distribution and exclusions:** build or inspect the package archive used by `create-project`; verify `.specs/`, `.git`, `.env`, `vendor/`, and generated assets are absent, while application source, `.env.example`, README, lock file, and `.gitignore` are present. Test: archive contents and clean-install inspection.
- **Documentation and optional workflow:** verify README commands, PHP/Composer requirements, environment setup, Docker startup, manual migration/status, app URL, production/shared-hosting distinction, backup and deploy constraints, and SDD Lite's canonical link/current installation reference; confirm no SDD Lite files or Composer dependency are required for application setup. Test: documentation review and link check.
- **Home content and visual accessibility:** check both locale catalogs have matching keys and aligned meaning; confirm the concise Composer/Docker/migration quick start, included features and limitations, links to full deployment/customization instructions, and official technology links. Inspect local SVG labels, accessible names, contrast/responsive layout, and loading without a third-party icon host. Test: locale-key validation and browser checks for both locales.
- **Technology references:** verify each external link targets the official project or maintained documentation and identifies the role of that dependency in the skeleton. Test: link review.
- **Compatibility:** validate `composer.json`/`composer.lock` and install the generated project without changing existing application contracts. Run focused Composer validation and the applicable application checks at Code/Review; no checks have been run during Spec.

**Applicable gate:** during Code, validate Composer metadata and the actual generated archive/installation, inspect populated-directory failure and Git history, and run focused checks for changed documentation, locale catalogs, SVG assets, and Home rendering. During Review, run `git diff --check`, recheck archive exclusions, document/link accuracy and accessible Home rendering in both locales; use `./tools/test-all.sh` if browser coverage is justified by the changed Home, once and with required services available. A real Packagist install cannot be claimed until package registration and publication are performed separately.
