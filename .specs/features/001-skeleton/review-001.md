# REVIEW-001 — Skeleton PHP/Slim/Vue

**Spec auditada:** [spec.md](spec.md) · **Data:** 15/10/2026 · **Estado:** correções abertas · **Próxima auditoria:** `review-002.md`

Esta review é o plano executável de correções. `R001-XX` é o identificador estável para commits futuros, testes e reauditoria. Todos os itens abaixo estão abertos; a especificação histórica foi movida sem modificar requisitos, decisões, checkboxes ou registros de fases. Quando a correção contrariar uma decisão histórica, registrar a decisão nova sem apagar a antiga.

## Base observada

- `docker compose ps -a`: app ativo e MySQL saudável. `docker compose exec -T app composer test`: **64 testes, 265 assertions, aprovado** (PHP 8.4.26/PHPUnit 11.5.57). Há ruído de `dubious ownership` do Git e stack traces de exceções esperadas no log de teste.
- `./tools/test-all.sh`: primeira execução no sandbox falhou no Chromium com `setsockopt: Operation not permitted`; repetição com permissão escalada **aprovou 10 rotas e a mesma suíte PHPUnit**.
- `docker compose exec -T app composer validate --no-check-publish`: válido; avisou sobre ausência de campo `license`. Não foram executadas migrations, rollback, testes de SMTP real, cobertura, PHPStan, PHP-CS-Fixer nem ensaio de deploy atrás de proxy TLS. Não há `composer quality` ou ferramentas estáticas configuradas no `composer.json` atual.
- Verificações positivas de código: cadastro persiste `USER` (`MysqlUserRepository.php:12`), login usa `password_verify` e regenera ID de sessão (`AuthService.php:32`, `AuthController.php:53`), logout destrói sessão (`AuthController.php:66`), CMS confere ADMIN no servidor (`ContentControllerSupport.php:14`), PDO desativa emulação de prepared statements (`ConnectionFactory.php:21`), Markdown escapa HTML bruto e bloqueia links inseguros (`MarkdownRenderer.php:15`), migrations CMS/Auth recusam rollback com dados (`20261015000002_create_cms_tables.php:80`, `20261015000003_create_auth_tables.php:27`). Não foi demonstrada exploração de SQL injection nem XSS nestes caminhos.

## Correções em ordem de execução

### Alta — segurança e integridade

- [x] **R001-01 · mudança de requisito / defeito funcional para a nova meta.** `src/Application/Auth/AuthService.php:37-45`, `src/Infrastructure/Http/Controller/AuthController.php:85-105`, `src/Infrastructure/Mail/SmtpPasswordResetMailer.php:9`, `database/migrations/20261015000003_create_auth_tables.php:10`, `public/assets/js/pages/Auth.js:21-25`, `README.md:24`. **Evidência:** o reset só é entregue por e-mail; sem SMTP configurado, a API responde 202 genérico e nenhum usuário recebe o segredo. **Impacto:** a recuperação prometida na spec antiga não funciona em clone mínimo e contraria a nova decisão de operar sem SMTP. **Solução:** especificar e implementar lote de códigos criptograficamente aleatórios com entropia adequada, hashes persistidos, uso único e exibição uma única vez ao usuário autenticado; permitir regenerar somente após reautenticação, invalidando lote anterior. No reset, aceitar um código e nova senha, sem recuperação pública por e-mail. Definir orientação clara sobre guarda dos códigos e perda de todos eles, sem prometer recuperação impossível; preservar User customizável e migrar schema de forma aditiva, sem editar migration aplicada. Remover SMTP e telas/contratos antigos somente após migração de API, OpenAPI, docs e testes. **Aceite:** após geração, resposta subsequente não revela códigos; banco contém apenas hashes; cada código funciona uma vez; regeneração exige senha atual, invalida lote anterior; o fluxo funciona sem SMTP. **Testes:** unidade para geração/uso/regeneração; integração MySQL para unicidade, concorrência e migração com dados; HTTP para autenticação, CSRF, autorização, rate limit, resposta e OpenAPI; SPA para exibição única e reset.
- [x] **R001-02 · defeito comprovado.** `src/Application/Auth/AuthService.php:50-55`, `src/Infrastructure/Database/Repository/MysqlUserRepository.php:15-16`. **Evidência:** `consumeResetToken()` confirma transação antes de `replacePassword()`; falha na gravação da senha consome o token permanentemente. **Impacto:** usuário pode perder a única chance de reset sem ter a senha alterada. **Solução:** no fluxo atual, tornar verificação, consumo, atualização de senha e invalidação dos demais segredos uma operação atômica; aplicar a mesma garantia aos futuros códigos de R001-01. **Aceite:** falha de update preserva código válido; sucesso altera senha e impede reuso. **Testes:** integração com erro induzido na atualização e duas tentativas concorrentes do mesmo código.
- [x] **R001-03 · defeito comprovado e risco potencial.** `src/Application/Auth/AuthService.php:27-30,48-55`, `src/Infrastructure/Database/Repository/MysqlUserRepository.php:17`. **Evidência:** há limite em cadastro, login e solicitação de reset, mas `reset()` não chama `recordAttempt`; login usa chave e-mail+IP, permitindo muitas tentativas de contas diferentes a partir da mesma origem. **Impacto:** tentativas ilimitadas sobre segredo de recuperação, credential stuffing distribuído por contas e carga no banco. **Solução:** limitar reset e combinar limites por origem/conta de forma proporcional, sem revelar existência de conta; projetar janela e limpeza proporcionais. **Aceite:** limite é aplicado antes de consultar/consumir código, cobre várias contas da mesma origem e libera após a janela. **Testes:** HTTP para limiar, janela, origens e contas distintas e não enumeração; integração de armazenamento.
- [x] **R001-04 · risco potencial relevante em produção.** `src/Infrastructure/Http/Middleware/SessionMiddleware.php:19`, `compose.prod.yaml:8-25`, `README.md:44-49`. **Evidência:** cookie `Secure` é decidido pelo scheme do request recebido pelo Apache; produção documenta TLS terminado em proxy e encaminhamento de `X-Forwarded-Proto`, mas o código não configura middleware de proxy confiável. **Impacto:** atrás de TLS externo e HTTP interno o cookie pode sair sem `Secure`; confiar cegamente no cabeçalho também permitiria spoofing. **Solução:** definir política de proxy confiável ou exigir cookie Secure por configuração de produção HTTPS, validando `APP_URL` e proxies aceitos. **Aceite:** HTTPS externo produz cookie Secure, HTTP local funciona como documentado, cabeçalho de cliente não confiável não altera a decisão. **Testes:** integração de cookie em cenários de proxy confiável/não confiável e smoke em proxy TLS.
- [x] **R001-05 · risco potencial.** `src/Infrastructure/Http/Middleware/CsrfMiddleware.php:11-16`, `src/Infrastructure/Http/Controller/MarkdownPreviewController.php:19`. **Evidência:** proteção depende dos prefixos `/api/auth/` e `/api/admin/`; um novo endpoint autenticado fora deles não recebe CSRF por padrão. **Impacto:** extensão do skeleton pode abrir mutação autenticada por cookie sem proteção. **Solução:** aplicar regra a toda mutação autenticada por cookie, com exceções explícitas e revisáveis, ou vincular exigência à rota/grupo; não alterar contrato atual sem teste. **Aceite:** nova rota mutável autenticada é bloqueada sem token independentemente do prefixo; anônimas seguem política declarada. **Testes:** integração com rota de extensão fictícia, todos os verbos mutáveis e exceções explícitas.
- [x] **R001-16 · risco potencial após troca de senha.** `src/Application/Auth/AuthService.php:48-55`, `src/Infrastructure/Http/Controller/AuthController.php:53-55`, `src/Infrastructure/Http/Middleware/SessionMiddleware.php:14-22`. **Evidência:** reset altera hash, mas sessões previamente autenticadas guardam apenas `user_id`; não há versão de sessão ou invalidação por troca de senha. **Impacto:** uma sessão roubada pode permanecer válida após recuperação. **Solução:** introduzir revogação de sessões por usuário ou versão de credencial consultada no backend, sem acoplar Auth a Posts/Pages. **Aceite:** sessão anterior deixa de acessar área autenticada após reset/regeneração de códigos conforme política documentada; sessão atual segue fluxo explícito. **Testes:** integração com duas sessões e troca de senha, incluindo ADMIN.

Remover flag específica do núcleo depois de preservar compatibilidade Plan no módulo legado. **Aceite:** um módulo de exemplo é adicionado/removido mudando só composição de entrada do projeto e seu módulo, sem filtros por filename no roteador comum; regressão Plan continua verde. **Testes:** arquitetura para presença/ausência de módulo, rota e binding; PHPUnit existente.
