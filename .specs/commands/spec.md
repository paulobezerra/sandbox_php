# SDD Lite · Spec

Turn a `feature.md` into a chosen and verifiable technical solution. Read `AGENTS.md`, [workflow](../guidelines/workflow.md), [specification](../guidelines/specification.md), [implementation](../guidelines/implementation.md), and the [template](../templates/spec.md). One invocation performs Spec only; it does not start Plan or Code.

Before starting, apply the [multi-agent chat isolation rule](../guidelines/workflow.md#recommended-isolation-one-command-per-new-chat). If this conversation has already been used for another command, warn about the quality risk, recommend a new chat, and do not block the user. If they explicitly insist, proceed and state in the delivery that they authorized the exception. End after Spec; any technical choice needed belongs to this execution.

## 1. Check the baseline and input quality

1. Identify the feature by ID or context. If candidates cannot be distinguished, ask for the ID. Check explicit user validation for Spec in `feature.md`, with name and OS date. If missing, apply the [entry rule](../guidelines/workflow.md#entry-premise-explicit-validation-of-the-previous-step). Check the recorded branch; for a Feature predating the branch rule, establish the branch and complete this metadata in `feature.md` without changing decisions. Read the Feature and inspect directly affected files, contracts, tests, data, and consumers. Distinguish verified current behavior, assumptions, and desired behavior; record differences between a historical Spec and actual code.
2. Find gaps that prevent a decision: actor, permission, initial state, action, result, failure, data to preserve, or scope boundary. If the Feature needs more precision, state exactly what is missing and why it affects the solution; ask only for essential product choices before proposing architecture. Do not fill silence with an invented contract.

## 2. Technical decision

1. Start only from assumptions checked in the Feature and code, distinguishing facts, assumptions, and product wishes. Present **one or more** real solutions, with no fixed numeric limit and no artificial alternatives; include keeping the current design when it meets the Feature. If one solution is clearly indicated by the constraints, briefly say why and proceed. If technical choices have meaningful tradeoffs, present only options that help the user decide, as vertical text blocks rather than a horizontal table. For each option, state estimated code impact as **low, moderate, or high**, affected components, and why. Assess security, data integrity, performance, compatibility/migration, simplicity, maintenance, and operations only where they distinguish options; mark irrelevant criteria as not applicable. Explain concrete costs and risks, cite available evidence, and recommend an option without mechanical scoring.
2. When there is a real technical choice, ask the user to choose or adjust the solution and **wait for the decision**. If the choice was already expressed in this conversation, use it without asking again. An agent recommendation is not approval. Before the decision, do not write the final `spec.md` or proceed to Plan/Code. For a clearly evident single solution, record the verified technical justification in the Spec without inventing user approval.

## 3. Specify and check

1. After the required choice, or after identifying one clearly evident solution, write `spec.md` with the solution, date, reason, and relevant tradeoffs. Assign stable requirement IDs. For each relevant behavior, describe initial state, action, and observable result, including success, invalid input, denied access, and partial failure where relevant. Define contracts, invariants, data transitions, migration, and affected consumers at the level needed for acceptance.
2. Link every requirement to a verification method proportional to risk. Check consistency with the Feature, stack and repository rules, current code, and existing contracts. **Do not change `feature.md`**, including when a later decision contradicts it. In that case, record the original Feature statement, the divergent decision, and its impact in the Spec; ask the user to explicitly validate the deviation and treat it as current only after recording that validation in the Spec. Resolve routine details in the Spec. Do not mark implementation progress here.
3. Leave Spec validation for Plan pending in `spec.md` until the user explicitly states it; the earlier technical decision does not count. After the statement, record it only in that field with the user's name and the OS date, without rewriting requirements or decisions. Deliver the link, recorded decision, and any essential open question. Stop before Plan or Code.
