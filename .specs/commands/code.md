# SDD Lite · Code

Execute **one open ID** from `plan.md`, or one correction identified in `review.md`, per invocation. Read `AGENTS.md`, [workflow](../guidelines/workflow.md), [implementation](../guidelines/implementation.md), and [quality](../guidelines/quality.md). The Spec defines the target; code and tests show the actual baseline. For the historical skeleton, follow only the explicitly requested item or phase. Do not proceed to another ID or Review in this execution.

Before starting, apply the [multi-agent chat isolation rule](../guidelines/workflow.md#recommended-isolation-one-command-per-new-chat). If this conversation has already been used for another command, warn about the quality risk, recommend a new chat, and do not block the user. If they explicitly insist, proceed and state in the delivery that they authorized the exception. End after the selected ID, even if blocked; another ID requires a new chat or a new warning.

## 1. Fix the scope before editing

1. Identify the feature and read Feature, Spec, Plan, and Review when present. Before the first Code ID, check the Plan's user validation in `plan.md`; **do not require approval for every iteration**. Use the ID supplied by the user; without one, choose the first open and eligible Plan task or the first ready Review correction. State the ID, associated requirements, and observable expected result. For the historical skeleton, use its existing IDs and acceptance criteria.
2. Check task order and dependencies in the Plan. For every prerequisite, confirm it is marked complete **and** that the diff, code, and tests show the implementation; a checkbox alone is insufficient. If the requested ID is not ready, explain the dependency and do not implement it. Compare the planned contract with code, tests, and affected consumers. If a decision would change the product or solution, record it briefly in the relevant Plan item and obtain the user's explicit response before the divergent work; do not rewrite Feature, Spec, or the original task acceptance. Resolve routine implementation questions here.
3. Inspect workspace state and relevant diff to separate pre-existing changes. Identify paths needed for the slice: domain, persistence/migration, API/OpenAPI, SPA, documentation, and operations as applicable. Internally plan the smallest sequence that satisfies the full acceptance.

## 2. Implement and gather evidence

1. For new or corrected behavior, first write a test that fails **for the expected reason**. Before refactoring existing behavior, characterize the contract that must remain. Make the smallest change that turns the test green, then refactor with tests green. For documentation-only or configuration-only work, use a check capable of detecting a real error when possible; do not invent a test that merely confirms the written text.
2. Complete the vertical slice, including affected consumers. Preserve HTTP contracts and existing data unless an approved decision says otherwise. Use a new migration when an applied schema must remain compatible; database reset, destructive rollback, or volume cleanup requires explicit authorization and target verification. When risk depends on integration, test at that boundary: HTTP/authorization/CSRF, MySQL/transaction, browser, or deployment configuration. A unit test alone does not prove the flow.
3. Run focused tests during the work. If a test fails, distinguish a task regression, a pre-existing failure, and an environment block with evidence. Fix issues within this ID; do not expand into unrelated refactoring. Continue independent parts of the same ID when partially blocked.

## 3. Verify the complete increment

1. Compare the result with **every** acceptance criterion for the ID and its cited requirements. Check success, relevant failure, legacy preservation, and updated affected contracts/documents. For edited PHP, run `composer format`, review the diff, and run `composer lint`. Follow commands and environment in `AGENTS.md` and `quality.md`; run full `composer quality` before finishing. SPA changes require `./tools/test-all.sh` with `app` active. Record commands actually run, results, and limits.
2. **Do not change Feature or Spec.** For a Plan task, mark only its checkbox in `plan.md` after acceptance and gates are proven; do not change scope or acceptance. Report commands and results in the session delivery. For a Review correction, implement the finding without creating an execution file; the next Review checks the result in `review.md`. Do not create per-task validation records or other artifacts.
3. If acceptance or a gate fails, leave the Plan item open and report the failure, evidence, and next step to complete **that same ID**. Do not claim success for a test that was not run. Deliver a concise result, tests, and pending work.
