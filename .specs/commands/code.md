# SDD Lite · Code

Execute **um ID aberto** do `plan.md` ou da review ativa por invocação. Leia `AGENTS.md`, [workflow](../guidelines/workflow.md), [implementation](../guidelines/implementation.md) e [quality](../guidelines/quality.md). A spec define o alvo; o código e os testes mostram a base real. Para o skeleton histórico, respeite o item ou fase explicitamente pedido. Não avance para outro ID ou para Review nesta execução.

Aplique antes de começar a [premissa máxima de um comando por chat novo](../guidelines/workflow.md#premissa-máxima-um-comando-por-chat-novo). Encerre este chat após o ID escolhido, inclusive se ele ficar bloqueado; outro ID exige outro chat.

## 1. Fixar o escopo antes de editar

1. Identifique a funcionalidade e leia sua feature, spec, plan e review ativa, quando existirem. Antes de implementar, confira a validação explícita do usuário para iniciar Code no plan ou na review ativa, com nome e data do SO. Se faltar, aplique a [regra de entrada](../guidelines/workflow.md#premissa-de-entrada-validação-explícita-do-passo-anterior). Use o ID indicado pelo usuário; sem ID, siga a sequência do plan ou da review e escolha o primeiro ID aberto elegível. Declare o ID, os requisitos associados e o resultado observável esperado. Se os artefatos históricos não usarem `TNNN-XX`, use o identificador e aceite existentes.
2. Confira se o ID está aberto e é o próximo permitido pela ordem e dependências do plan ou da review. Comprove no código, nos testes e nos registros que todos os pré-requisitos estão implementados e verificados; não confie apenas nos checkboxes nem peça aprovação do usuário para essa checagem técnica. Se o ID indicado não estiver pronto, explique a dependência e não implemente essa tarefa. Confira se o aceite permite distinguir sucesso de falha. Compare o contrato planejado com o código, os testes e os consumidores afetados. Se houver contradição que mude o produto ou a solução escolhida, registre-a e resolva na etapa dona da decisão antes de implementar. Dúvidas rotineiras de implementação são resolvidas aqui.
3. Inspecione o estado do workspace e o diff pertinente para separar alterações preexistentes. Identifique os caminhos necessários à fatia: domínio, persistência/migration, API/OpenAPI, SPA, documentação e operação, conforme o caso. Planeje internamente a menor sequência que entrega o aceite inteiro.

## 2. Implementar e obter evidência

1. Para comportamento novo ou corrigido, escreva primeiro um teste que falhe **pelo motivo esperado**. Antes de refatorar comportamento existente, caracterize o contrato que deve permanecer. Faça a menor mudança que torne o teste verde e refatore com os testes verdes. Para mudanças apenas documentais ou de configuração, use uma verificação capaz de detectar erro real quando possível; não invente teste que só confirme o texto escrito.
2. Complete a fatia vertical, incluindo os consumidores afetados. Preserve contratos HTTP e dados existentes salvo decisão registrada. Use migration nova para alterar schema já aplicado; não faça reset, rollback destrutivo ou limpeza de volumes. Quando o risco depender de integração, teste nessa fronteira: HTTP/autorização/CSRF, MySQL/transação, navegador ou configuração de deploy. Um unitário isolado não comprova esse fluxo.
3. Rode testes focados durante o trabalho. Se um teste falhar, distinga erro introduzido pela tarefa, falha preexistente e bloqueio do ambiente com evidência. Corrija o que pertence ao ID; não amplie o escopo para refatorações independentes. Avance em partes independentes do mesmo ID quando houver bloqueio parcial.

## 3. Verificar o incremento completo

1. Compare o resultado com **cada** aceite do ID e com os requisitos citados. Verifique casos de sucesso, falha relevante, preservação do legado e atualização dos contratos/documentos afetados. Para PHP editado, rode `composer format`, revise o diff e rode `composer lint`. Siga os comandos e o ambiente de `AGENTS.md` e `quality.md`; rode `composer quality` antes de concluir. Mudanças na SPA exigem `./tools/test-all.sh` com `app` ativo. Registre comandos realmente executados, resultados e limites.
2. Só marque `[x]` no plan ou na review se o comportamento aceito e todos os gates aplicáveis passaram. No registro do ID, cite data, arquivos relevantes, teste vermelho e verde observados, gate e limites; ligue a correção ao achado anterior quando houver. Deixe a validação do usuário para Review pendente até sua declaração explícita; ela não condiciona o próximo ID de Code. Atualize checkboxes da spec apenas com comprovação do requisito integrado. Preserve o estado histórico de `todolist.md` e de reviews anteriores.
3. Se o aceite ou gate falhar, mantenha o ID aberto. Relate o que está pronto, a falha com sua evidência, o risco residual e o próximo passo para concluir **esse mesmo ID**. Não declare sucesso por teste não executado. Entregue ao usuário o resultado funcional, os testes e pendências de forma curta.
