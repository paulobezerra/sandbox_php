# SDD Lite · Code

Execute **um ID aberto** do `plan.md` ou uma correção apontada por `review.md` por invocação. Leia `AGENTS.md`, [workflow](../guidelines/workflow.md), [implementation](../guidelines/implementation.md) e [quality](../guidelines/quality.md). A spec define o alvo; o código e os testes mostram a base real. Para o skeleton histórico, respeite o item ou fase explicitamente pedido. Não avance para outro ID ou para Review nesta execução.

Aplique antes de começar a [regra multiagente de isolamento do chat](../guidelines/workflow.md#isolamento-recomendado-um-comando-por-chat-novo). Se esta conversa já foi usada para outro comando, avise do risco à qualidade, recomende um chat novo e não bloqueie o usuário; se ele insistir explicitamente, prossiga e reafirme na entrega que autorizou a quebra do fluxo. Encerre a etapa após o ID escolhido, inclusive se ele ficar bloqueado; outro ID pede novo chat ou novo aviso.

## 1. Fixar o escopo antes de editar

1. Identifique a funcionalidade e leia Feature, Spec, Plan e Review quando existir. Antes do primeiro ID de Code, confira a validação do Plan no próprio `plan.md`; **não exija aprovação do usuário a cada iteração**. Use o ID indicado pelo usuário; sem ID, escolha a primeira tarefa aberta e elegível do Plan ou a primeira correção pronta da Review. Declare o ID, os requisitos associados e o resultado observável esperado. Para o skeleton histórico, use os IDs e aceites existentes.
2. Confira a ordem e as dependências no checklist do Plan. Para cada pré-requisito, confirme que está marcado como concluído **e** que o diff, o código e os testes mostram sua implementação real; checkbox isolado não basta. Se o ID indicado não estiver pronto, explique a dependência e não o implemente. Compare o contrato planejado com código, testes e consumidores afetados. Se surgir decisão que mude produto ou solução, registre-a brevemente no item pertinente do Plan e obtenha resposta explícita do usuário antes da parte divergente; não reescreva Feature ou Spec nem o aceite original da tarefa. Dúvidas rotineiras de implementação são resolvidas aqui.
3. Inspecione o estado do workspace e o diff pertinente para separar alterações preexistentes. Identifique os caminhos necessários à fatia: domínio, persistência/migration, API/OpenAPI, SPA, documentação e operação, conforme o caso. Planeje internamente a menor sequência que entrega o aceite inteiro.

## 2. Implementar e obter evidência

1. Para comportamento novo ou corrigido, escreva primeiro um teste que falhe **pelo motivo esperado**. Antes de refatorar comportamento existente, caracterize o contrato que deve permanecer. Faça a menor mudança que torne o teste verde e refatore com os testes verdes. Para mudanças apenas documentais ou de configuração, use uma verificação capaz de detectar erro real quando possível; não invente teste que só confirme o texto escrito.
2. Complete a fatia vertical, incluindo os consumidores afetados. Preserve contratos HTTP e dados existentes salvo decisão e autorização registradas. Use migration nova para alterar schema já aplicado quando houver compatibilidade a preservar; reset, rollback destrutivo ou limpeza de volumes exigem autorização explícita e conferência do alvo. Quando o risco depender de integração, teste nessa fronteira: HTTP/autorização/CSRF, MySQL/transação, navegador ou configuração de deploy. Um unitário isolado não comprova esse fluxo.
3. Rode testes focados durante o trabalho. Se um teste falhar, distinga erro introduzido pela tarefa, falha preexistente e bloqueio do ambiente com evidência. Corrija o que pertence ao ID; não amplie o escopo para refatorações independentes. Avance em partes independentes do mesmo ID quando houver bloqueio parcial.

## 3. Verificar o incremento completo

1. Compare o resultado com **cada** aceite do ID e com os requisitos citados. Verifique casos de sucesso, falha relevante, preservação do legado e atualização dos contratos/documentos afetados. Para PHP editado, rode `composer format`, revise o diff e rode `composer lint`. Siga os comandos e o ambiente de `AGENTS.md` e `quality.md`; rode `composer quality` antes de concluir. Mudanças na SPA exigem `./tools/test-all.sh` com `app` ativo. Registre comandos realmente executados, resultados e limites.
2. **Não altere Feature ou Spec.** Para uma tarefa do Plan, marque apenas seu checkbox em `plan.md` após aceite e gates comprovados; não altere escopo ou aceite. Informe comandos e resultados na entrega da sessão. Para correção de Review, implemente o achado sem criar arquivo de execução; a próxima Review confere o resultado em `review.md`. Não crie validação por tarefa nem outro artefato.
3. Se o aceite ou gate falhar, deixe o item do Plan aberto e relate a falha, sua evidência e o próximo passo para concluir **esse mesmo ID**. Não declare sucesso por teste não executado. Entregue ao usuário resultado, testes e pendências de forma curta.
